# 巨大 MySQL テーブルの全件カウント ガイドライン

対象は、行数も内容も分からない巨大なMySQLテーブルについて、稼働中サービスへの影響を抑えながら全件数を知りたい開発者です。暗号化された50〜100列の表を含みます。論理削除・履歴も含め、業務上のWHEREを付けない全行を数えます。InnoDBでは読み取りビューから見える行が対象で、未コミット行やディスク上の全バージョンを足す意味ではありません。

**最初は既存メタ情報で規模を把握します。ただし、未知の任意のInnoDB表について「誤差数%以内」と「本番への無影響」を両立する汎用手法は、この検証では得られていません。** 数%が高価なら10%程度も許容する、という判断を先に置きます。その許容誤差・鮮度・負荷予算の中で、既存の信頼できる件数管理、条件を検証した推定、許容する時点の正確なCOUNTを比較します。内容の復号や行データの取り出しは不要です。

現MATRIXの対象系列は8.4 LTS、9.7 LTS、26.10 Innovationです。主な計測は8.4.13、比較は [lab.rb](../lab.rb) のMATRIXを参照してください。数値はローカルCompose環境での方式比較であり、本番の所要時間ではありません。引用した過去観測は `results/reference/20261107-observations/` にハッシュ付きで保存し、再実行の生成結果と区別します。詳細なSQL、テーブル設計ごとの根拠、ロック実験は [検証詳細](table-count-evidence.md) にあります。未完の検証は末尾に示します。今回の白紙実行はRubyの構文解析で失敗し、実験へ到達していません。既存の数値を今回の再測定結果とは扱いません。

想定はprimaryと非同期replicaです。まず取得先・共有ストレージ・実際の分離レベル・エンジン・表/ビュー・鍵の利用可否・監視/停止権限を確認します。ラボはノートPC上の4 CPU Docker VM、bind mount、通常1.5 GBのバッファプールです。matrixの追加実験は256 MBを使います。絶対時間は移植せず、baselineの揺らぎ以下の差や短窓のtailを効果と認定しません。

| 現MATRIXの対象系列（サポート状況は再確認待ち） | ラボで確認するもの |
|---|---|
| 8.4 LTS | 基本動作と主な負荷比較。負荷の本計測は8.4.13のみ |
| 9.7 LTS | 基本動作・SQL互換性。負荷結果を横展開しない |
| 26.10 Innovation | 同上 |

[保存済みmatrix結果](table-count-evidence.md#2-前提環境)とMATRIXを対応させます。8.0等は現MATRIXの対象外です。サポート中のMySQLだけを案内する方針ですが、各系列の期限・現行版の公式原文はこの執筆ステップでは未確認で、公開前の確認事項です。

## 1. 必要な精度と取得先を選ぶ

最初に、対象テーブル群、許容誤差、許容する取得時点、概算の保証が必要かを決めます。複数シャード・テナントの対象一覧と移行中の所有先も固定します。

| 必要な結果 | 第一候補 | 得られるものと条件 |
|---|---|---|
| とにかく規模を知る参考値 | `TABLE_ROWS`、統計キャッシュを迂回 | 速い統計値。数%の誤差上限は保証しない |
| 3%・5%・10%を目指す条件付き概算 | 同じ構造・変更特性の表で校正した推定、既存カウンタ | 校正した条件と不確かさを付ける。反復の安定性だけでは校正にならない |
| 少し古くてもよい正確値 | 余力のある専用read replica、既存バックアップの隔離復元先でCOUNT | その読み取りビューまたは復元時点の正確値。primary現在値との差は別問題 |
| primary上の正確値 | 負荷予算を満たす上限付きCOUNT | 1文の読み取りビューの正確値。初回の試行にも負荷がある |
| 長い1文を避けて全域を数える | 短いトランザクションで分割 | 文ごとの合計。同時更新があると一瞬の正確値にはならない |
| 頻繁に取得する | 整合した初期件数＋カウンタ/CDC、変更しない範囲の確定値再利用 | 書き込み・削除・再試行・移行・TRUNCATEを正しく追跡する運用が必要 |

精度目標を緩めると標本数を減らせる可能性がありますが、実現誤差・区間目標・全対象の信頼度は別です。10%を許容する場合も3%・5%用を含めて費用を比較します。判定時点が違うため、緩い目標が常に安いとは限りません。3/5/10%の同条件コスト比較01cと100列TDEの3/10%負荷比較01dは、今回の白紙実行では未実行です。5%のサービス負荷比較は未計測です。

統計が小さく見えても「COUNTして安全」とは判断しません。過小推定、古い値、取得不可を区別できないまま進めると、巨大表を小表として扱ってしまいます。

専用レプリカへの通常のCOUNTは、適用を止めなくても実行できます。共用レプリカでは読み取りサービスと適用処理への影響を監視します。適用停止は、その時点を固定する必要がある場合に所有者が扱う別の運用です。遅延秒数が0でも、primary現在値との差が0件または数%以内だとは保証できません。許容時点を満たせない場合は、整合した差分管理や所有者との追加検証が必要です。

## 2. 最初に取得する参考値

新しい専用接続で、対象スキーマ・表を指定します。大量の表を一斉巡回せず、DB・共有ストレージごとに開始時刻と同時実行数を調整します。以下のSQLは既存統計の読み取りだけです。

```sql
SET SESSION autocommit = 1;
SET SESSION lock_wait_timeout = 3;
SET SESSION information_schema_stats_expiry = 0;
SELECT TABLE_SCHEMA, TABLE_NAME, TABLE_TYPE, ENGINE,
       TABLE_ROWS, DATA_LENGTH, INDEX_LENGTH, CREATE_OPTIONS
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'db' AND TABLE_NAME = 't';
```

`db`と`t`は対象名へ置き換えます。3秒はラボの待ち上限の例で、サービス共通の安全値ではありません。呼出し側にも待ち時間と全体時間の予算を設け、失敗時に無制限に再試行しません。結果なし・NULL・権限不足・タイムアウトは「0件」にしません。VIEWなら、基底表の件数が欲しいのか、ビューの結果行数が欲しいのかを確認します。

`information_schema_stats_expiry=0`は統計キャッシュを迂回する設定です。真値の取得や統計の再作成ではありません。**この手順にはANALYZEを追加しません。** ANALYZEは権限、待機、I/O、実行計画の変化、binlogへの記録とレプリカの再解析を所有者が扱う別の保守操作です。サンプルページ数の増量も本番の共通設定にはしません。

### メタ情報の比較

以下の推定値同士は同じ統計に由来する場合があり、値の一致を独立した検証とは扱えません。レプリカでも取得できますが、統計と初期化状態は取得先の状態です。

| 方法 | 精度と鮮度 | 権限と利点 | 制約と待ち |
|---|---|---|---|
| `TABLES.TABLE_ROWS` | InnoDBは統計の推定。既定キャッシュは古い値や0を返し得る | 対象表のSELECTだけで取得できた。最初の候補 | `expiry=0`でも再計算前・標本誤差は残る。サイズ情報も概数 |
| `SHOW TABLE STATUS` のRows | 上記と同様。セッションのexpiry設定に注意 | SELECTだけで取得できた。既存ツールで使いやすい | 名前一致は`WHERE Name='t'`を使う。LIKEの`_`や`%`はワイルドカード |
| `mysql.innodb_table_stats.n_rows` | 永続統計の再計算時点の推定 | キャッシュを経由しない参照候補 | システム表へのSELECTが別途必要。非永続統計・パーティション名の扱いに注意 |
| `INNODB_TABLESTATS.NUM_ROWS` | メモリ上の推定。未コミットDMLも反映し得る | 初期化状態も調べられる | PROCESSが必要。`STATS_INITIALIZED`を併読し、未初期化0を空表と扱わない。DDLの後ろで待った |
| `EXPLAIN` のrows | 実行計画の推定。COUNTの完了見込みではない | SELECTだけで取得できた。読む索引も確認可能 | 保留DDLの後ろで待った。参考値だけなら最初から必須にはしない。`EXPLAIN ANALYZE`は実クエリを実行するので代用しない |
| `PARTITIONS.TABLE_ROWS` の合計 | 各パーティションの推定の合計 | パーティション別の偏りを見る候補 | 同一時点・独立した裏付けではない。NULLや取得不可を0として合算しない |
| AUTO_INCREMENT、`MAX-MIN+1` | 発行済みIDの範囲。行数ではない | 件数取得の代用にはしない | 欠番、削除、予約、UUID・Snowflakeで桁違いに外れる |

権限・DDL待ちの比較は [レプリカ実験](../results/reference/20261107-observations/requested_metadata_on_replica.json) の`privileges`、`waits_on_primary`、`waits_on_replica_applier_ddl`によります。primary・replica各1条件で、全構成の無待機を保証するものではありません。`super_read_only`下でもメタ情報は読めましたが、ANALYZEは1290で拒否されました。通常のANALYZEはログを抑制しなければ複製され、各サーバーで再計算されます。

### 誤差は何%だったか

[58表の初回比較](../results/reference/20261107-observations/requested_metadata_accuracy_initial.json) では、初回の`TABLE_ROWS`は`expiry=0`で54表が5%以内、最大絶対誤差12.152%でした。ANALYZE後でも54表が5%以内、最大16.591%です。既定キャッシュのままでは最大100%でした。これは構成した表の観測分布で、本番の成功確率や保証された上限ではありません。

同実験では、行サイズが偏る表の20サンプルページで38.731%の誤差もありました。サンプルを増やしても任意の精度を保証するものではありません。初回実験のNUM_ROWSは初期化状態を記録していないため、そのまま精度比較へ採用しません。[初期化状態を併読した再試験](../results/reference/20261107-observations/requested_metadata_accuracy.json) では、54表がANALYZE後にUninitializedとなり、推定誤差の集計から除外しました。未初期化と空表を区別する必要があります。

レプリカでは、統計誤差と未適用分を分けます。実験ではprimaryが2200万行、適用停止中のreplicaが2000万行の状態でも、replicaの統計はその2000万行に対してさらに約2.916%小さい値でした。primary現在値に対する誤差とは異なります。`analyze_is_local`では、ログを抑制したANALYZEが実行先の統計だけを変えることも確認しました。

### 数%の信頼区間を計算する別案

単一の整数主キーがある場合は、キー空間のセルを一様に復元抽出し、各セルの件数から全体を推定する候補があります。データ内容や復号は不要です。1セルの件数の上限を一意整数キーから定め、観測分散だけで空標本の不確かさを0にせず、確率的な境界を計算します。

[初回のTDE実験](../results/reference/20261107-observations/requested_probability_sampling.json) では、幅広い300万行の合成表で512回の範囲COUNTにより目標3%幅の区間へ達し、所要0.2121〜0.7286秒、比較の全件COUNTは2.6516〜2.8437秒でした。一方、細い表では全件COUNTが速く、巨大な欠番・密集域の表では8192回でも精度未達でした。単純な合成表・無サービス負荷・継承したキャッシュでの比較であり、初回速度や50/100列の本番影響を一般化する根拠にはしません。

適用には、同一スナップショット、一意整数キー、規定どおりの抽出・判定が必要です。95%という信頼度は実現誤差の絶対保証ではありません。複数表や再実行の全体で信頼度を求めるなら、全対象・全判定へ誤差確率を割り当てます。疎なキー空間では、読み取り予算内に数%へ達しないことがあります。

スナップショットはMIN/MAX取得から終了までMDLと読み取りビューを保持し、undoやレプリカのDDL適用に影響し得ます。primaryの既定経路へは追加しません。精度・予算・後始末を別々に判定し、失敗や精度未達を全件数として返しません。[詳細仕様と制約](probability-count.md) を確認し、隔離先を含む所有者の検証後に限定採用します。

### 精度とコストが変わる条件

| 条件 | 参考統計・セル標本・正確COUNTへの作用 |
|---|---|
| 欠番が多い、密度が偏る | セル標本の区間が狭まりにくい。疎な表は10%でも達しない場合がある。PK範囲だけを件数にしない |
| 行サイズ・ページ密度が偏る | 統計の標本誤差が増え得る。ANALYZEやページ増量後も1回ごとの改善は単調ではない |
| 小さい索引がある | 全件COUNTが標本より安くなる場合がある。精度を落とす前に比較する |
| TDE、幅広い行、キャッシュ、MVCC | 主にI/O・CPU・時間が変わり、同じ予算内で到達できる標本精度が変わる。完了したスナップショットCOUNTの精度は落ちない |
| 同時更新・replica遅延 | 対象時点・母集団が変わる。推定誤差と鮮度の差を別に示す |

保存済みの100列TDE・無サービス負荷の比較は次のとおりです（同じ[01b結果](../results/reference/20261107-wide-sampling/results/requested_probability_wide_100.json)の`static`、継承キャッシュ）。標本は3%区間目標で、実現誤差の絶対保証ではありません。

| 索引条件 | 正確COUNTの秒 | セル標本の秒 | この条件での選択候補 |
|---|---|---|---|
| 小さい二次索引なし | 6.8817〜8.1966 | 0.7568〜1.0313 | 精度・予算を満たした標本 |
| 小さい二次索引あり | 0.0494〜0.0723 | 1.1712〜3.1946 | より短く正確なCOUNT |

同じ[01b結果](../results/reference/20261107-wide-sampling/results/requested_probability_wide_100.json)の`service`では、標本は全体1秒予算に索引なし6/6、あり3/6で到達しました。静的な速さはサービスSLO合格を意味せず、10%緩和で改善するかは未計測です。

これらの適用範囲と保持した根拠は[追加観測と比較計画](table-count-evidence.md#13-追加観測と比較計画)に示します。未知の表へ一律の最高速方式を選ぶことはできません。許容する誤差と時点を満たし、負荷・後始末も確認できた候補の中で読取量と時間を比較します。

## 3. 暗号化と50〜100列の扱い

**値の内容が分からなくても、全件数のために列の内容を調べたり復号式を実行したりする必要はありません。** `COUNT(*)`を使います。NULL可否も不明な列を`COUNT(col)`へ渡すと、NULLを除外した別の件数になります。

| 暗号化方式 | 全件数取得で考えること |
|---|---|
| InnoDBのTDE、表領域暗号化 | ページをストレージから読む際にエンジンが鍵を使う。正常に稼働し、表を開けることが前提。鍵が利用できず開けない場合は復旧担当へ依頼する |
| アプリケーション等による列暗号化 | 暗号文を解釈せず数える。保存幅、索引の有無、NULL可否が影響する。平文の意味・分布を前提にしない |
| ストレージ層の暗号化 | MySQLから見える索引構造とは別。実ストレージの性能・鍵管理はこのComposeでは未計測 |

50列と100列という数だけでは負荷は決まりません。選択される索引のバイト数、主キー幅、インライン行サイズ、キャッシュ、MVCCの可視性確認が影響します。外部LOBの総容量がそのままCOUNTの読取量になるとも限りません。小さい二次索引があれば読む量を減らせますが、同時更新によるクラスタ索引の参照が増える場合もあります。`FORCE INDEX(PRIMARY)`を全表共通の推奨にはしません。

TDEの比較は [91番の実装](../bench/requested/91-encrypted-count.py) による同一サーバー上の暗号化あり・なしです。8.4.13・9.7.4・26.10.0の3版で修正版が正常終了しました。各400万行、クラスタ索引は約396 MB、バッファプールは256 MBで、通常のSELECT COUNTの行ロックは0、REPEATABLE READのINSERT SELECTは10万件の観測上限に達しました。これは3列の比較で、50/100列との組み合わせも計測を終えましたが、旧負荷生成器と短い観測窓による診断であり、SLO合格の根拠にはしません。根拠は `results/reference/20261107-observations/requested_encrypted_count_<version>.json` の`count_default`、`sizes`、ロック項目です。「追い出し走査後」と「直後再実行」を同じキャッシュ状態とは扱いません。9.7.4と26.10.0では、直後再実行でも暗号化なしの読取0 bytesに対し暗号化ありが約113 MBを読む条件があり、暗号処理だけの倍率は分離できていません。本番primaryの無影響や暗号化の一律の倍率は主張しません。

### COUNTの書き方

| 書き方 | 意味と選択 |
|---|---|
| `COUNT(*)` | 全行。通常はこちらを使う |
| `COUNT(1)` | 全行。InnoDBではCOUNT(*)と同じ扱い。変更による高速化は前提にしない |
| `COUNT(id)` | idがNOT NULLなら全行。NULL可なら別の件数。列の内容が不明でもNULL可否はメタ情報で確認できる |
| `COUNT(col)` | NULL以外の値。非索引列なら読む量も増え得る。全件数の標準にはしない |

[60列表の順序検証](../results/reference/20261107-observations/requested_wide_form_order.json) は、4形式を順番を循環させて各8回、スレッド設定2種類で計64測定しました。既定設定の中央値はCOUNT(*) 2.565秒、COUNT(1) 2.067秒、COUNT(id) 3.409秒ですが、各範囲は大きく重なります。固定順の旧実験だけで「COUNT(*)が遅い」とは結論できません。64測定は揃いましたが、起動元の終了により実プロセス終了コードは回収できていません。追い出し走査後も対象ページは残留し、ホストキャッシュも制御できないため、この比較から全環境での同速や順位は保証しません。

## 4. 何行以下なら正確なCOUNTを試せるか

**共通の安全行数閾値は作りません。** 同じ行数でも、細い二次索引と幅広いクラスタ索引では読む量が違い、書き込みの形や余力によって所要時間も変わります。統計の過小推定に安全係数を掛けても、未知の表に対する許可条件にはなりません。

負荷予算を決めた後の最小例です。`db`/`t`はメタ情報で確認した識別子に置換します。EXPLAIN自体にも待ち上限を適用します。

```sql
SET SESSION autocommit=1;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET SESSION lock_wait_timeout=3;
SET SESSION max_execution_time=1000; -- ラボ例。初回にも所有者の予算が必要
EXPLAIN SELECT COUNT(*) FROM `db`.`t`;
SELECT COUNT(*) FROM `db`.`t`;
```

`bench/count_preflight.py`でエンジン・索引・NULL・複合キー・分割可否を調べます。EXPLAINのkeyは実際の内部読取索引の証明ではなく、rangeでも次の境界探索が狙いどおりとは限りません。実測例と分割SQLは[詳細§2とSQL 4](table-count-evidence.md)へ。索引・統計・接続先が変わったら再確認し、PRIMARYがない表にその名前を強制しません。DDLが競合中なら開始しません。

過去の同条件の実績があれば、読む索引の推定バイト数と利用可能な読取帯域から所要時間の目安を作り、CPU・MVCCの追加コストを考慮します【推論】。推定索引バイト数÷余剰帯域は計画の補助であり、実行時間や無影響の保証ではありません。中断されたCOUNTは一般に進捗率を返さず、中断時間から残時間や総行数を外挿しません。

初回の試行にも、次の条件を満たします。決められない場合はprimaryで試さず、参考統計または余力のある隔離先を使います。

1. サービス所有者が、アプリのp95/p99遅延・エラー率、CPU、I/O待ち・帯域・IOPS、ストレージの余力を基に開始条件と停止条件を記録する。平均やp50だけでは判断しない。
2. 実行前の基準値を取り、DDL・バックアップとの調整先を確認する。同一DBと共有資源での同時実行上限を設ける。
3. 新しい専用接続からトップレベルのSELECTだけを使い、autocommit、分離レベル、セッションの実行時間上限、MDL待ち上限を明示する。ラボの1000msを既定の安全値として採用しない。
4. 別接続・別スレッドの監視と、ジョブの停止フラグ、KILLを含む停止確認を用意する。クライアントのタイムアウトや切断だけでサーバー処理の終了を決めつけない。
5. 終了後も回復を観測する。時間上限はCPU・I/O・キャッシュ追い出しの上限ではなく、中断しても消費済み資源やキャッシュは即座には戻らない。

監視対象には、対象表のPENDING MDL、FLUSH待ち、想定外の行ロック、undoのHLL、replica遅延を含めます。監視不能、監視の失敗、接続先の変化でも停止します。詳細な計装確認・エラー分類・停止手順は [検証詳細のSQL 0、M、2と§8](table-count-evidence.md) を参照してください。未完了・未着手リクエストがある計測の遅延分布は打切り観測であり、SLO合格には使いません。停止後に上限を延ばして自動再試行しません。

**通常のトップレベル`SELECT COUNT(*)`は行ロックを取りません。ただしMDLと資源負荷はあります。** `INSERT ... SELECT COUNT(*)`等は分離レベルによって読み取り元の行をロックする場合があります。`SET @c=(SELECT COUNT(*))`、`FOR SHARE`等も同じ扱いにはできません。結果はクライアントで受け、保存は別の文で行います。文の形ごとの実測は [lock_factors.json](../results/reference/20261107-observations/lock_factors.json) と検証詳細§5にあります。

分割は、1文あたりのMDL保持とundo滞留を短くする候補です。全域を読む総負荷をなくすものではありません。複合キー、NULL、文字列の照合、ENUM、TIMESTAMP、DESC、更新されるキー、再開時の表世代などの条件があるため、独自のOFFSET全域走査へ置き換えず、検証詳細の設計別条件を確認します。途中で止まった合計は全件数として返しません。

## 5. 代替方法を選ぶ条件

| 方法 | 有利になる条件 | 費用と限界 |
|---|---|---|
| 既存の専用read replicaでCOUNT | primaryへの走査を避け、適用済み状態の時点を許容できる | replica自身の負荷・適用遅延は残る。同じストレージを共有していればprimaryも無影響とは限らない |
| 既存バックアップを隔離先へ復元してCOUNT | バックアップ時点でよく、本番で試行する余力がない | 復元容量・時間・鍵へのアクセスが必要。新規バックアップ取得を無影響とは扱わない【復元全体の負荷は未計測】 |
| 既存カウンタ、基準件数＋CDC | 頻繁な取得が必要 | 初期件数と差分位置、コミット、重複排除、削除・TRUNCATE・移行への対応が必要。差分だけでは未知の絶対件数は得られない【CDCは未計測】 |
| 不変な閉じた期間・パーティションの確定件数を再利用 | 大半のデータが変更されない | 遅延到着・削除・EXCHANGE等で前提が崩れる。TABLE_IDやUPDATE_TIMEが一致しても不変の証明にはならない |
| 条件を限定した確率的・層化サンプリング | 抽出単位と包含確率を定義でき、同種サービス群で校正できる | ランダムI/Oと範囲COUNTが必要。空標本・予算到達・偏在時に精度未達を返す。任意の未知分布への低コスト保証はない【代替の層化方式は未計測】 |
| 小さい索引の追加 | 今後も繰り返し数え、維持費を上回る | 索引作成時のDDL・I/O、保存容量、書き込み負担が増える。1回の件数取得のために無条件で追加しない |

キー範囲標本の既存実験は、固定seedでランダムな区間を抽出したものです。欠番の多い表で大きく外れたため、この方式を共通手順にはしません。他の標本設計まで一括で否定する根拠ではありません。[別案の比較実験](../results/reference/20261107-observations/requested_54-EXP-SOL-9.json) を参照してください。

## 6. 社内導入時の確認とFAQ

サービスごとに以下を記録します。権限や責任者が未定なら、primary COUNTとレプリカ適用停止の経路を開始しません。参考統計の取得と、所有者への精度確認依頼は継続できます。

| 項目 | 記録する内容 |
|---|---|
| 件数の意味 | 対象一覧、物理行数、論理削除・履歴を含むこと、許容誤差・時点 |
| 取得先と共有資源 | primary/replica/復元先、DB識別子、共有ストレージ・読み取りサービス、同時実行上限 |
| 実行と停止 | 実行責任者、監視担当、停止権限、監視周期、失敗時の連絡先 |
| 運用調整 | DDL・バックアップの確認先、実行時間帯、負荷予算、回復の確認条件 |
| 適用停止を使う場合 | 所有者、チャネル、元の状態、停止要求失敗時の継続監視者、再開とGTID追いつきの確認者 |
| 結果に添付するもの | 取得時刻・取得先・方式、対象世代、推定/正確値の区別、対象時点・鮮度、誤差を保証できる範囲、完了/未完了の内訳 |

- **SELECT権限しかない場合は？** TABLE_ROWS等の参考値は取得できます。監視・停止できないまま精度を求めて本番COUNTを実行せず、所有者へ依頼します。
- **統計同士が一致し、ANALYZE後も安定していれば数%以内？** 保証できません。同じ統計への依存と標本誤差が残ります。
- **暗号化され、値の内容が分からない場合は？** 全件数に内容の解釈は不要です。暗号化方式と索引・行幅を確認し、列の復号式をCOUNTへ追加しません。
- **COUNT(1)やCOUNT(id)に変えると速い？** 高速化の前提にはしません。idがNULL可なら件数も変わります。全件数はCOUNT(*)を標準にします。
- **1秒で止めれば数十msのSLOを守れる？** 守れるとは言えません。実行中と終了後の資源影響は別に測ります。
- **共用replicaならprimaryへの影響はなくなる？** 共有I/O等の影響が残り得ます。replicaの読み取りと適用を含めて予算を決めます。
- **適用停止でエラーが返ったら？** 後から停止が効く場合があります。元の状態への復旧を確認するまで所有者が監視を引き継ぎ、「復旧済み」と早まって報告しません。
- **複数サービスが同時に実行してよい？** 個別の低負荷でも合計負荷は増えます。DBと共有資源単位で制御します。
- **一部シャードが失敗したら？** 部分成功として内訳を返します。失敗した対象を0件として全件合計にしません。移行中の二重計上も避けます。
- **マネージド環境のキャンセルでよい？** 製品の操作がサーバー処理を終了させるか所有者が確認します。本ラボでは未計測です。

`bench/`はこのCompose環境専用です。本番接続用の配布ツールではありません。詳細SQLを組み込む場合も、上記の監視・停止・復旧を実装して所有者が確認します。
