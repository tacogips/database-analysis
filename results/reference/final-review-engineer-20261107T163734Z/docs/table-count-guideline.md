# 巨大MySQLテーブルの件数取得ガイドライン

対象はサポート中のMySQLのInnoDBで、業務上のWHEREを付けない全行の件数です。行データ取得・条件付き件数・サポート切れの版は対象外です。
取得先の版・構成・所有者を確認します。検証版は8.4 / 9.7 / 26.10系、基本負荷は8.4.13です（[実行証明](../results/reviews/final-all-proof.json)）。採用時のサポート状況は所有者が再確認します。
**台帳の初回収集は既存統計、数%の精度や正確値が必要なら資源を隔離した取得先へ進む**ことを既定にします。

## 1. 最初に取る情報と判断フロー

1. 対象DB・表・所有者、必要な精度、許容時点、取得期限を決めます。移行中の二重計上にも注意します。
2. **最初は既存の承認済み台帳・監視のエクスポートを確認**します。追加取得が必要なら、所有者と取得先・追加I/O/CPU・待機・監視・取消の予算を決めてから下のSQLへ進みます。
3. 参考値で足りれば、推定であることと取得先・時刻を付けて終了します。
4. 校正済みの条件に合えば、[校正手順](table-count-calibration.md)に従って誤差の経験的な見込みを添えます。保証とは区別します。
5. 数%以内が必須、正確値が必要、または校正を棄却した場合は、専用replicaか隔離復元・計測DBへ進みます。
6. 必要な取得先や予算がなければ、必要な設備・精度緩和・鮮度緩和を示して保留します。未知の値を0件にしません。

**追加primary影響を許せない、予算や監視がない場合はSQLへ進まず**、既存エクスポート・隔離先取得か保留を選びます。
SQLはアプリのpoolや既存トランザクションを再利用せず、対象限定の読取権限を持つ**新規専用接続**で実行します。既存接続でautocommit=1にすると無関係の処理をcommitし得ます。
まず設定だけ確認します。3秒・1000msは例で、§4の所有者予算に置き換え、接続・設定に失敗したら止めます。

```sql
SET SESSION autocommit = 1;
SET SESSION lock_wait_timeout = 3;
SET SESSION max_execution_time = 1000;
SELECT @@version, @@session.transaction_isolation,
       @@session.information_schema_stats_expiry;
```

既にexpiry=0なら毎回エンジン統計を取得します。非0でも未キャッシュ・期限切れならエンジンへ取得に行くため、**cache-onlyの保証にはなりません**。
この追加取得も予算内で許可された取得先だけで、対象名を置き換え、次を実行します。許可がなければ保留します。

```sql
SELECT TABLE_SCHEMA, TABLE_NAME, TABLE_TYPE, ENGINE, TABLE_ROWS,
       AVG_ROW_LENGTH, DATA_LENGTH, INDEX_LENGTH, CREATE_OPTIONS,
       UPDATE_TIME
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'db' AND TABLE_NAME IN ('t');
```

大量の表はDB・共有ストレージ単位で小分けにし、同時実行数と総時間を制限します。
既存の統計キャッシュを利用し、`information_schema_stats_expiry=0`を自動設定しません。`ANALYZE TABLE`も件数収集の自動手順にしません。
`UPDATE_TIME`は統計更新時刻ではなく、NULLや制約もあるため鮮度判定をこれだけで済ませません。
グローバル設定を変えず、小分け収集にも期限・停止予算を設けます。統計参照にも影響ゼロは約束できません。
TABLE_ROWS=0も空表を独立に確認できなければUNKNOWN（参考統計0は別欄）です。結果なし・NULL・未初期化・権限不足・エラー・タイムアウトはUNKNOWNと理由を保存します。
VIEW・非InnoDB・対象世代不明はこのCOUNT手順へ自動投入せず、所有者に対象を確認します。

| 必要な結果 | 選択 | 返すもの |
|---|---|---|
| 台帳・規模の把握 | 既存のTABLE_ROWS等 | 参考統計。誤差上限なし |
| 誤差の見込みを知りたい | 類似条件で真値と照合した統計 | 校正条件・観測誤差・棄却条件付きの経験値 |
| 条件付きの確率的区間が使える | 隔離先で検証済みの標本prototype | 適用条件・信頼度・精度未達を明記 |
| 数%以内が必須／正確値 | 資源を隔離した取得先のCOUNT(*) | その読み取りビューの正確値 |
| primaryの現在値が必要 | 件数管理・差分追跡等も含め設計判断 | 隔離先の過去値を現在の正確値と表示しない |

## 2. 統計をどこまで信じるか

InnoDBのTABLE_ROWSは推定です。[公式TABLES仕様](https://dev.mysql.com/doc/refman/8.4/en/information-schema-tables-table.html)も正確な行数とはしていません。
SHOW TABLE STATUSのRows、永続統計のn_rows、EXPLAINのrowsは同じ統計に依存することがあり、一致しても独立した検証になりません。
EXPLAIN ANALYZEは実クエリを実行するので、軽い統計参照として使いません。AUTO_INCREMENTやMAX−MIN+1は件数ではありません。

**未校正のTABLE_ROWSが小さいことをprimaryの無制限COUNTの許可にしません。** 行数だけで安全閾値を決めず、行幅、索引バイト数、PK幅、キャッシュ、更新、DDLを確認します。
列数だけから読取量も推定しません。DATA_LENGTH/INDEX_LENGTHは割当量の概数で、COUNTが実際に読むバイト数ではありません。
詳細な代表表の選び方、統計の誤差、100Mや幅広いTDE表の観測範囲は[校正手順](table-count-calibration.md)へ分離します。
[観測極値の比較表](table-count-calibration.md#2-観測した最大最小誤差と条件)は旧観測と新しい白紙実行を分けています。小表の誤差0%やページ数増量を全表の保証にせず、標本prototypeの未達結果とも分けます。
論理復元・再構築ではページ配置や統計が変わります。復元表の誤差を元の本番キャッシュ統計へ移さず、同じ世代・時点の統計と真値を対応付けます（[校正§3](table-count-calibration.md#3-非本番で真値と照合する)）。

統計年齢、変更量、サンプルページ数は劣化の兆候を診断する材料です。これらから分布に依存しない誤差上限は出せません。
`INNODB_TABLESTATS`のSTATS_INITIALIZED・MODIFIED_COUNTERは管理者による任意確認です。PROCESSが必要なので、既定で権限追加を求めません。
未初期化や取得不可を空表と判断しない点は[公式TABLESTATS仕様](https://dev.mysql.com/doc/refman/8.4/en/information-schema-innodb-tablestats-table.html)も参照してください。
ページ数増量やANALYZEはI/Oと実行計画への影響があり、個々の推定が必ず改善するわけでもありません。校正は非本番で行います。

## 3. 正確値を取る実行先とSQL

**監視より先に資源分離と所有者のCPU/I/O等の上限を確立**します。監視は競合の予防そのものではありません。
既存の承認済みbackup/replica・構築手順を使います。backup取得・replica新設自体もprimaryへ負荷を掛け得るため、準備作業も所有者予算内で行います。
専用replicaでもCPU・I/O・ストレージ・通常読取トラフィックと複製適用への影響を確認します。
共用replicaやprimaryとストレージを共有する構成は、自動的に安全とはしません。共有ホスト・ディスク・ネットワークの影響を隔離・制限できなければ、承認済み手順で隔離復元先を用意します。用意できなければ保留します。
replica遅延、取得元、GTID等の位置、取得開始・終了時刻を記録します。遅延0秒でもprimary現在値との件数一致を保証しません。
復元先ではバックアップ時点と適用済みログ位置を記録します。鮮度が不足するなら、その条件では要求を満たせないと返します。
隔離先では既存索引と通常EXPLAINを確認し、まず既定のCOUNTを候補にします。狭い既存索引のCOUNTが標本より速い例もあります（[校正§4](table-count-calibration.md#4-代表fixtureと条件付き標本の位置付け)）。
EXPLAINは実読取索引・I/O・安全性の保証ではありません。PRIMARY強制や索引の新設をprimaryの件数収集の既定にしません。

以下は**隔離先で、監視・キャンセル担当を決めてから**使う例です。DB/table識別子は安全に引用し、専用の新規接続を使います。

```sql
SET SESSION autocommit = 1;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET SESSION lock_wait_timeout = 3;
SET SESSION max_execution_time = 1000;
SELECT CONNECTION_ID();
SELECT /* count_job: replace_with_unique_job_id */ COUNT(*) AS exact_rows FROM `db`.`t`;
```

1000msと3秒は予算の設定例であり、サービス安全性の保証値ではありません。RCまたはRRの通常SELECTを使います。
COUNT(*)はNULLも含め全行を数えます。COUNT(col)はNULLを除くので代用しません。COUNT(1)への変更を高速化策にはしません。
新規接続のautocommitの1文なら、そのCOUNTの読み取りビューに見える行の正確値です。未コミット行や全物理バージョンを数えるものではありません。
各表のCOUNTは別時点です。長い複数表snapshotを既定にせず、全表同時点が必要なら固定した隔離復元先等を用意します。
分割COUNTの合計も、更新中には単一時点の正確値になりません。[整合性読取の公式仕様](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)を参照してください。

通常のRC/RRのSELECT COUNT(*)は行ロックを取りませんが、MDLは取得します。DDL待ちやundo保持、資源競合は残ります。
FOR SHARE/FOR UPDATE、SERIALIZABLE内のCOUNT、LOCK TABLES/FTWRLはこの手順に追加しません。
INSERT ... SELECT COUNT(*)などのDML、CTAS、SETへCOUNTを埋め込む形も採用しません。通常SELECTと異なり、読み取り元をロックする場合があります。

## 4. 止められるジョブとして運用する

- 最初は1 DB・1表ずつ実行し、共有資源単位でも直列化します。実測した余力に基づいてのみ並列度を増やします。
- **事前**：実行担当・監視/取消担当と別の管理接続を確保し、平常時のp99・失敗率・CPU・IOPS/帯域/待ち・複製遅延・DDL待ち・長いread view/undoを確認します。
- 所有者が資源上限、観測間隔、停止値、回復確認窓を記録します。**SLO違反より手前に、検出・取消遅延分の余裕を持つ停止値**を置きます。余裕が見積もれなければ開始しません。
- 文の実行上限、MDL待ち上限、呼出し側の期限を併用します。時間上限だけでは短いSLOや後続影響を守れません。
- **実行中**：停止値への到達、監視不能、想定外のDDL/負荷があれば新規投入を止め、監視/取消担当が所有処理を停止します。
- 接続IDに加え一意なjobタグ・取得先・アカウント・開始文脈で**現在の所有クエリ**を照合してからKILL QUERYし、サーバー上の文・トランザクションの終了を確認します。古いIDの再利用先を盲目的にKILLしません。
- クライアント切断・タイムアウトを停止完了と扱いません。終了未確認なら所有者が追跡し、次の表へ進みません。
- **終了後**：キャッシュ/I/Oの影響は文終了後も残り得ます。所有者の回復窓まで同じ指標を追い、予算内へ戻ることを確認します。取消直後に盲目的な再試行をしません。失敗はUNKNOWNと理由を保存します。
- 実験完了、要求精度、サービス予算、後始末を別々に判定します。未開始・未完了リクエストを除いてSLO合格にしません。

開始前に所有処理の識別・取消・終了確認ができない場合は、所有者の運用経路を用意するまでCOUNTを保留します。SQL時間上限だけでは代用できません。
primary全表COUNTの代わりとなる常時件数管理は、初期値とINSERT/DELETE・再試行・移行・TRUNCATEの整合を設計した別機能です。

## 5. 暗号化・幅広い表の分岐

| 状態 | 判断 |
|---|---|
| TDEでサーバーが必要な鍵を利用可能 | SQLクライアントが鍵やseedを知らなくてもCOUNT可能。通常の取得先・予算判断へ進む |
| 暗号化バックアップの復元 | 管理者が必要なkeyring・鍵・復元手順を用意する。ファイルだけからCOUNTできると約束しない |
| サーバーが必要な復号能力を持たない／SQLで読めない | 本手順では取得不可。復旧・権限・SQL取得経路が必要 |
| アプリ側で列を暗号化、SQLで表を読める | 件数に平文の解釈は不要。COUNTへ復号式を追加しない |
| 80列・100列、外部LOBあり | 列数から費用を決めず、実際の索引・行幅・割当量・更新を確認する |

TDEの鍵利用は[公式暗号化仕様](https://dev.mysql.com/doc/refman/8.4/en/innodb-data-encryption.html)に従います。アプリ暗号化についてはCOUNTの意味からの推論で、実アプリ暗号化性能の実測ではありません。
**1億行・80列・TDEの組合せは未計測**です。既存の1億行の細い表と75万行の50/100列TDE表から、時間・容量・誤差を外挿しません。

## 6. 条件付き標本は補助候補

一意整数PKのキー空間を一様に抽出するprototypeは、固定snapshot、セル上限、抽出・停止規則、誤差確率の配分を満たす場合だけ検討します。
整数PKなし、極端な欠番や偏在、予算内に精度未達なら採用しません。反復値の安定だけでは認定しません。
確率的区間の信頼度、今回の実現誤差、将来の精度保証は別です。複数表・再実行を含めると信頼度の管理も必要です。
適用判定・既存の比較結果は[校正手順](table-count-calibration.md)と[prototype仕様](probability-count.md)を参照してください。primaryの台帳収集の既定にはしません。

## 7. 結果に添える情報と根拠の限界

保存する項目は、対象世代・取得先・方式・取得時刻・対象snapshot/復元時点・遅延、値/UNKNOWNと理由、校正条件、精度達成、負荷予算、停止・後始末の状態です。
参考統計、経験的な誤差見込み、条件付きprototype、正確snapshot COUNT、鮮度を別の欄で表示します。シャードの欠落やNULLを0として合計しません。

[所有者の実行証明](../results/reviews/final-all-proof.json)は、縮小した固定runnerの白紙allの終了コード0、意味・最終source・整合・後始末監査を認めています。根拠は[固定snapshot](../results/reference/review-20261107T155750Z-26743/manifest.json)と[所有者監査bundle](../results/reference/owner-acceptance-20261107T161659Z/manifest.json)です。
**実験完了・精度達成・サービス予算・後始末は別判定**です。精度未達や時間上限を残しており、本番SLO・全条件最速・一律の影響ゼロは認定していません。
初回縮小実行の逆転した壁時計窓は却下され、性能/SLO根拠に再利用しません。旧網羅gridの除外も成功測定ではありません（[証跡の区別](table-count-calibration.md#5-証跡と受入条件)）。
本番ストレージ、物理的なreplica分離、実アプリ暗号化、1億行80列TDE、5%目標のサービス負荷は未計測です。観測の絶対時間や誤差を自社へ保証として移しません。
benchmarkの実行証明だけでは文書を受け入れません。文書の受入れは、執筆とは別セッションで完了した最終Sol 2役それぞれのレビューが最終文書のSHA-256と所有者proofに一致し、[文書受入記録](../results/reviews/final-operational-review-acceptance.json)に受入れが記録されることを条件とします。
