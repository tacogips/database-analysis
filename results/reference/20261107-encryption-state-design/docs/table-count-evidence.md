# 巨大 MySQL テーブルの全件カウント 検証詳細

運用の入口は [ガイドライン](table-count-guideline.md) を参照してください。この付録は実験と詳細なSQLの根拠です。SQL内の時間値はラボの値で、全サービス共通の安全値ではありません。主文書の負荷予算と監視・復旧条件を満たしてから適用します。過去の負荷計測には、終了時に未着手リクエストを落とす旧実装が含まれます。飽和時の裾や未完了率を過小評価し得るため、これらからSLO合格を認定しません。COUNTの完了・ロック・I/Oの観測と、サービス性能の合格は別です。

最新の白紙実行は容量確認・初期照合を通過し、基本負荷試験中に所有者が中断しました（exit130、§16）。§1〜13の数値は明記した過去観測、§14の中断と§15の容量失敗は別試行の履歴です。今回の部分診断へ過去の数値を付け替えていません。[統合監査](table-count-integration-audit.md)で全結果・ログ、未解決要求、失敗の意味を確認してください。

根拠の表記: 【実測】= `results/` のファイル名を併記 / 【文書】= MySQL 公式マニュアル(§12)/ 【推論】= 仕組みからの推定 / 【未計測】= このラボでは測っていない / 【未実行】= SQL をラボで実行していない。ファイル名は `requested_` を省いて `10-EXP-O2-1-all-tables.json` のように書くことがあります(この付録の過去観測の実体は `results/reference/20261107-observations/requested_<名前>.json`、新規実行は `results/` 直下)。

## 1. 結論

| 必要な精度 | 実行するもの | 得られる値 | 行ロック |
|---|---|---|---|
| 精度保証のない参考値 | SQL 1 | 統計の推定値。数%以内が必要なら主文書§1の精度の分岐へ | なし |
| 実数(DDL とバックアップを排除でき、短時間で終わる) | SQL 2 → 打ち切られたら上限を延ばした 1 文。どの索引を読むかは、短い上限で試して決める。条件を満たさなければ分割かレプリカ(§7 の延長の条件) | 1 つのスナップショットの実数。測った範囲で最速 | なし |
| 実数(DDL を調整する必要がある) | 競合中は開始しない。所有者が調整後、短い分割等を予算内で検討 | **文ごとの値の合計**。誤差は実行中の変更数程度(§7) | なし |
| ある一瞬の実数 | §7 | 1 文のスナップショット、または適用を止めたレプリカの値 | なし |

分かっていること(8.4.13)【実測】。**1文が速い条件を観測しましたが、読む索引と負荷条件で結果は変わります。一般のサービス無影響は示していません**:

- **数える索引に書き込みが触れないとき、既定の 1 文は分割(待ちなし)の約半分の時間です。** 1 億行で中央値は 1 文 5.72〜6.90 秒、分割 10.71〜13.19 秒、2000 万行に毎秒 800 文の書き込みで 1.05 秒と 1.94 秒でした。どちらも事前に決めた基準(中央値が 20% 以上低く、範囲が重ならない)を満たします(`21-EXP-R8-a.json`, `22-EXP-R8-b.json`, `3d-EXP-O6-WRITE-MIX-nonindexed.json`、§3)。
- **作業セットをバッファプールの大部分に広げると差は基準を満たしません**(中央値 11.44 秒と 13.68 秒、範囲が重なる。`30`〜`35-EXP-R9-*.json`)。
- **索引更新・MVCCで小さい二次索引が安いとは限りません。** 旧`06`/`08`は二次索引の未完了とPRIMARYの完了を報告していますが、reqmix2は失敗を時間上限扱いにし得るため、確認済み打切り・必要反復・終了確認の再監査まで、その順位を採用根拠にしません（§14、SOL-PROTOCOL-001〜003）。別の0g保存観測は§13に条件付きで示します。
- **この負荷では分割も完走するとは限りません。以下は旧JSONの完了表示の内訳で、反復充足や失敗原因を再監査中です。** 毎秒 800 文の散らばる書き込みで、分割の完走は `k` が 4 回中 3 回、`PRIMARY` が 5 回中 1 回でした(同)。毎秒 100 文では比較の 24 回がすべて完走し、別に走らせた 3 回のうち索引列の更新の 1 回がステップ数の上限で止まりました(`05`, `07`, `09-*.json`)。完走しなければ途中の合計を使わず「分割できないとき」へ進みます。
- **分割の利点は時間ではなく、DDL の待ち行列と undo の滞留です。** `ALTER` の待ちは 1 文の残り時間そのものです(18.68 秒かかった回で 5 秒後に発行して 13.74 秒待ち、書き込み p50 は 5819.68 ms。`impact_mdl_long_count_then_ddl.json`)。分割では `ALTER` の待ちは INSTANT で 15.0〜141.3 ms です(§5)。
- **全域を読むと、1 文でも分割でも待ちを入れても、作業セットがバッファプールから追い出されます。** ミス率は対照の 0% に対し 2.07〜4.11% で、計測した 120 秒の間 0 に戻りませんでした。遅延の p50 に明確な悪化はなく、裾はノイズの範囲で判定できません(§3)。
- `EXPLAIN` は 0.105 ms、`TABLE_ROWS` は 0.194 ms で 99,619,308(実数 1 億、誤差 0.38%、`24-EXP-R10.json`)。ただし統計キャッシュで 0 や古い値を返します(§4)。

### 使ってよい文の形

**カウント専用のクライアントから直接発行する、トップレベルの `SELECT` だけを使います。** 値を保存するときは、結果をクライアントで受け取り、別の文で書き込みます。

次の形は読み取り元の全行をロックします(§5)。

```sql
SELECT COUNT(*) FROM t FOR SHARE;                    -- LOCK IN SHARE MODE も同じ
SET @c = (SELECT COUNT(*) FROM t);                   -- READ COMMITTED でも全行ロック
DO (SELECT COUNT(*) FROM t);                         -- 同上
PREPARE st FROM 'SET @c = (SELECT COUNT(*) FROM t)'; -- 同上。ルーチンの中の SET、トリガーの中も
INSERT INTO s SELECT COUNT(*) FROM t;                -- REPEATABLE READ で全行ロック
REPLACE INTO s SELECT COUNT(*) FROM t;               -- 同上
UPDATE s SET c = (SELECT COUNT(*) FROM t);           -- 同上
CREATE TEMPORARY TABLE x AS SELECT COUNT(*) FROM t;  -- 同上
LOCK TABLES t READ;                                  -- 行ロックはないが書き込みを止める
```

### コピーして使う SQL

`db`、`t`、列名、索引名は置き換えてください。`bench/` のスクリプトは検証環境専用で、本番に向けてはいけません。SQL 0、M、1、2、3、4 の文面はラボで実行しました(`12-EXP-6.json`)。下で【未実行】と書いたものを除きます。

**SQL 0: 接続設定(新規の専用接続で)**

```sql
SET SESSION autocommit = 1;          -- 0 だと文の間も MDL を保持する
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;   -- READ UNCOMMITTED の継承を防ぐ
SET SESSION lock_wait_timeout = 3;   -- 既定は 31536000 秒(1 年)
SET SESSION time_zone = '+00:00';    -- TIMESTAMP カーソルの夏時間の折り返しを避ける
SET NAMES utf8mb4;                   -- 文字列カーソルの変換損失を防ぐ
SET SESSION max_execution_time = 1000;  -- ヒントが失われたときの予備の上限(ms)
SELECT VERSION(), @@server_uuid, @@read_only, @@autocommit, @@transaction_isolation, @@time_zone, @@character_set_results;
```

- **接続プールの接続を使い回さないでください。** `START TRANSACTION` のあとで SQL 0 を実行しても、`@@autocommit`=1、`@@transaction_isolation`=REPEATABLE-READ と読めるのにトランザクションは続きます。この状態では文の間も `SHARED_READ` の MDL が残り、`ALTER` は 1205 で通りません。SERIALIZABLE のトランザクションなら行ロック(1003 件)も残り、`UPDATE` も 1205 です(`14-EXP-SOL-1.json`)【実測】。**読み返しでは見つかりません。**
- SQL 0 の前に `autocommit=0` の接続で開いていたトランザクションは、`SET SESSION autocommit = 1` で終わりました(`driver_autocommit_off`、`ALTER` が通る)。SQL 0 の後で `autocommit=0` に戻されると MDL が残ります(`autocommit_disabled_after_sql0`)【実測】。
- 実際に効いているかは、ステップの間に別の接続で確かめます(§8 の「ジョブの MDL」)。
- READ UNCOMMITTED は使いません。未コミットの 1,000 行を数えました(10 万行に対して 101,000)。継承した接続でも SQL 0 の後は 100,000 です。READ COMMITTED と REPEATABLE READ も 100,000 でした(`14-EXP-SOL-1.json`)【実測】。

**SQL M: 監視の確認(別の接続で)**

```sql
SELECT ENABLED FROM performance_schema.setup_instruments WHERE NAME = 'wait/lock/metadata/sql/mdl';  -- YES のこと
SELECT `count` FROM information_schema.INNODB_METRICS WHERE name = 'trx_rseg_history_len';
SELECT COUNT(*) FROM information_schema.INNODB_TRX;
```

MDL の計装を無効にすると、実際に DDL が待っていても `metadata_locks` の PENDING は 0 件でした。有効なら 1 件です(`45-EXP-SOL-6.json`)。この状態で SQL M は開始を拒否し、監視も `monitor_not_ready` で止まりました【実測】。エラー、NO、空の結果のいずれも「待ちなし」と扱わず、開始しないでください。必要な権限は §8 にあります。

監視できない環境で実行してよいのは、SQL 0 を設定した接続での SQL 1 だけです。実数が必要なら、監視できる環境を用意します。

**SQL 1: 概数**

```sql
SET SESSION information_schema_stats_expiry = 0;   -- キャッシュでなく最新の統計を読む
SELECT TABLE_ROWS, DATA_LENGTH, INDEX_LENGTH, ENGINE, TABLE_TYPE
FROM information_schema.TABLES WHERE TABLE_SCHEMA = 'db' AND TABLE_NAME = 't';
-- 以下は読む索引を確認するときだけ。参考統計の取得に必須ではない。保留DDLの後ろで待つ場合がある。
EXPLAIN SELECT COUNT(*) FROM t;                    -- rows を読む
```

`expiry=0` のとき、`TABLE_ROWS` と `EXPLAIN` の `rows` は全実験で同じ値でした(`24-EXP-R10.json`)【実測】。同じ統計に由来するので、一致は正しさの保証になりません。`MAX(id)-MIN(id)+1` は使いません。

**SQL 2: 時間上限付きの 1 文**

以下の1000msはラボの比較条件です。初回試行にも主文書§4の負荷予算が必要で、サービス共通の安全値ではありません。実行者が決めた上限へ置き換え、監視・停止確認を含む経路でだけ実行します。

```sql
SELECT /*+ MAX_EXECUTION_TIME(1000) */ COUNT(*) FROM t;
```

- クライアントから直接発行します。**ストアドプログラムの中では、ヒントもセッション上限も効きません。** `CALL` の中のヒント 1000 ms は 4,472 ms まで走って成功し、セッション上限 1000 ms の `CALL` は所有者が 5 秒で止めるまで走りました。イベントの中のヒントも 6 秒時点で実行中でした(`13-EXP-O2-2.json` の `hint_context_SOL_8`)【実測】。
- 1000 ms は判断値です。DDL が来たときにサービスが待てる時間より短くしてください。`t_dense` で 1000.33〜1000.37 ms、500 ms で 500.32〜500.36 ms に返りました(`12-EXP-6.json`)。`t_repl` は 1107.6 ms で、上限を 107 ms 超えた例もあります(`10-EXP-O2-1-all-tables.json`)【実測】。
- セッション上限とヒントはどちらの向きでもヒントが優先しました。セッション 1000 + ヒント 3000 は 3000 ms、セッション 3000 + ヒント 1000 は 1000 ms、セッション 1000 + ヒントなしは 1000 ms です(`12-EXP-6.json`)【実測】。
- 上限の 2 倍を超えて成功した文があれば、ヒントもセッション上限も効いていないので、そのジョブを止めて経路(プロキシ、SQL 生成層)を調べます。ヒントを除いた分割はこの規則で 3 回とも止まり(`stopped:long_success`、`3a-EXP-O6-LOOP-RULES.json`)、ヒントなしの単独の文は上限 1000 ms に対し 4,222 ms で検知されました(`3b-EXP-6-monitor.json`)【実測】。

**打ち切りの判定(SQL 2, SQL 4 共通)**

時間切れの番号は 1317 と 3024 が混在し(65 回中 1317 が 55 回、3024 が 10 回)、同じ文でも変わります。`KILL` も 1317 です。**番号でも経過時間でも原因は分かりません。** 代わりに同じ接続で、エラーの直後にカウンタの増分を見ます。

```sql
SHOW SESSION STATUS LIKE 'Max_execution_time_exceeded';   -- 開始時と、エラーの直後に読んで比べる
```

| 判定方法 | 時間切れ 25 回 | 先に KILL された 19 回 |
|---|---|---|
| カウンタの増分 | 25 回すべて増えた → 時間切れ | **19 回すべて増えない → 停止** |
| 経過時間(上限以上なら時間切れ) | 25 回とも時間切れ | **5 回を時間切れと誤判定**(1317 の処理が上限の後になった場合) |

出典は `13-EXP-O2-2.json` の `summary`、成功した文の増分は 0 です(`10-EXP-O2-1-all-tables.json`)【実測】。上限を過ぎてから届いた `KILL` はカウンタが増えて時間切れと判定されます(`limit_1000_kill_at_1000` など)。その `KILL` は止める文がもうなく、**ジョブは次の文へ進みます。人が止めるときは `KILL QUERY` ではなく、ジョブの停止フラグか `KILL <接続 ID>` を使ってください。** 接続ごと切ると 2013 で止まりました(`13-EXP-O2-2.json` の `connection_lost`)【実測】。

この判定は `bench/countlib.py` の `split_count` に組み込み、ループを通して確かめました。時間切れ 5 回はすべて幅を半分にして続行し、第三者の `KILL` 5 回はすべて `stopped:killed_not_timer` で止まりました(`3a-EXP-O6-LOOP-RULES.json`)【実測】。

**MDL 待ちは 1205 になるとは限りません。** 文の上限が `lock_wait_timeout` より短いと、保留中の DDL の後ろで待つ文は時間切れになります。ヒント 500 ms、`lock_wait_timeout` 3 秒で 3024 が返りました。**時間切れの後は、幅を変える前に対象表の PENDING を確認します**(§8 の SQL)。この規則で 5 回とも `stopped:mdl_pending` で止まり、分割不可と誤判定しなくなりました(同)【実測】。カウント用の利用者が `performance_schema` を読めないなら、監視の接続で確かめます。

**SQL 3: 分割に使う索引を選ぶ**

```sql
SELECT s.INDEX_NAME, s.SEQ_IN_INDEX, s.COLUMN_NAME, s.COLLATION, s.NON_UNIQUE, s.NULLABLE,
       s.INDEX_TYPE, s.SUB_PART, s.IS_VISIBLE, s.EXPRESSION, c.DATA_TYPE, c.EXTRA
FROM information_schema.STATISTICS s
LEFT JOIN information_schema.COLUMNS c
  ON c.TABLE_SCHEMA = s.TABLE_SCHEMA AND c.TABLE_NAME = s.TABLE_NAME AND c.COLUMN_NAME = s.COLUMN_NAME
WHERE s.TABLE_SCHEMA = 'db' AND s.TABLE_NAME = 't' ORDER BY s.INDEX_NAME, s.SEQ_IN_INDEX;

SELECT index_name, stat_value AS pages FROM mysql.innodb_index_stats
WHERE database_name = 'db' AND table_name = 't' AND stat_name = 'size';
```

使える索引の条件です。**主キーを末尾に足す場合は、その列も条件の対象です。** 権限のない利用者では `STATISTICS` がエラーでなく 0 行を返します(`44-EXP-R13.json`)。0 行を「索引なし」と読まないでください【実測】。

| 条件 | 理由 |
|---|---|
| `INDEX_TYPE='BTREE'`, `IS_VISIBLE='YES'`, `SUB_PART IS NULL`, `EXPRESSION IS NULL` | 順序があり値全体を表す。多値索引は 1 行が複数の項目を持つ【文書】 |
| 全キー部の `COLLATION='A'`。例外は単一列 `PRIMARY` の DESC(`d_desc_pk` で実測) | 方向が合わないと filesort になり、読む量が 25 倍になる(999 → 25,000 行、全 5 版、`11-EXP-O2-1-versions-*.json` の `R3_desc`)【実測】 |
| 先頭以外の列はすべて NOT NULL | NULL 可の非先頭列を持つ索引をカーソルにすると、**2 万行のうち 500 行しか数えず、エラーも出ない**(全 5 版、同ファイルの `R2_nullable_composite`)【実測】 |
| 先頭列も NOT NULL が望ましい | NULL の `COUNT` が分割されない 1 文になる(`t_uniq_nullable` で 104.5 ms)。ほかに候補がないときだけ使う |
| `DATA_TYPE` が `enum`, `set`, `float`, `bit` でない | ENUM の数値カーソルは読み取りが位置に比例する(下記)。強制して歩くと SET は 1 万行を 6,667 行、FLOAT は往復の確認なしで 10,032 行と**エラーなしで誤り**ました。BIT は往復の確認で止まりました(全 5 版、`3c-EXP-O2-1-versions-*.json`)【実測】 |
| `double` は最後の手段 | ドライバとチェックポイントが値を無損失で扱えることが前提 |
| `EXTRA` に `on update` がなく、実行中に値を更新しない列。生成列は依存元の列も更新しないこと。`DEFAULT_GENERATED` は式の既定値を示すだけで、この条件に当たらない。分からなければ使わない | 値が動くと二重に数えるか数え損なう(§7)【実測】 |

条件を満たす中でページ数が最小のものを選び、統計を読めなければ `PRIMARY` を選びます。

- 負荷下で `k_created` と `PRIMARY` を比べました。`PRIMARY` の時間は約 1.4 倍でした(§8)。
- パーティション表の統計は `table_name='t#p#p1'` の形です。`table_name='t'` では何も返りません(`12-EXP-6.json`)【実測】。`LIKE` で探すときは `_` をエスケープします(`t\_part#p#%`)。
- 何もなければ「分割できないとき」へ進みます。**ENUM 先頭の主キーしかない表は、値ごとに `c = 'label' AND id > ?` で歩けます。** 数値カーソルは後ろの値ほど読み取りが増え、1 ステップの `Handler_read_next` が 100 万 / 500 万 / 2000 万行で 989,999 / 4,989,999 / 19,989,999、時間が 76.87 / 590.59 / 2329.22 ms です。値ごとの条件は 9,999 行、1.19〜1.70 ms で変わらず、2000 万行の歩行は 198 ステップ、最長 12.5 ms で正しい件数でした(`53-EXP-R1.json`)【実測】。
  **値ごとの歩行の前に、次の文で先頭の内部番号を確かめ、0 なら分割しません。** 非 strict モードで入った不正な値は内部番号 0 の空文字になり、どのラベルにも属しません。内部番号 0 を 700 行混ぜた 30,700 行の表で、ラベルを列挙する歩行は 30,000 行と**エラーなしで数え損ない**、定義に `''` がある表でも同じでした。この確認は 3 版のどちらの表でも歩行を拒否し、番号 0 のない表は通して 30,000 行で一致しました(`01-EXP-S8-ENUM-DOMAIN-*.json`)【実測】。`c = ''` では見分けられません(定義の `''` にしか一致しない表があるので、番号で確かめます)。現在の SQL モードが strict でも、古い行が残っていることは排除できません。

  ```sql
  SELECT /*+ MAX_EXECUTION_TIME(500) */ c+0 FROM t FORCE INDEX (`PRIMARY`) ORDER BY c, id LIMIT 1;   -- 0 なら「分割できないとき」へ
  ```

**SQL 4: 分割カウント**

各ステップは「`N` 件先のキー」だけをサーバーに尋ねるので、行はクライアントへ送られません。この手順を `bench/countlib.py` の `split_count` に同じ文面で実装し、対象 51 表すべてで `COUNT(*)` と一致しました。残り 7 表は手順どおり分割しない表です(`10-EXP-O2-1-all-tables.json`)【実測】。空表、幅未満、幅ちょうど、負の値、NULL の少数と多数、大量の同値も全 5 版で一致しました(`11-EXP-O2-1-versions-*.json` の `sizes_and_nulls`)【実測】。

索引によって形が 2 つあります。カーソルの列は、形 A は索引の列 + 足りなければ主キー、形 B は索引の先頭列です。`N` は幅です。**どちらの形でも、先頭列が NULL 可なら、最初に NULL の行を 1 回だけ数えて足します。**

```sql
-- 先頭列が NULL 可のときだけ。最初に 1 回
SELECT /*+ MAX_EXECUTION_TIME(500) */ COUNT(*) FROM t FORCE INDEX (`i`) WHERE c IS NULL;
```

**形 A: カーソルが一意になる**(主キー、NOT NULL のユニーク索引、二次索引 + 主キー)。行が返るたびに **`N` を足します**。

```sql
-- 最初(a が先頭列)。N=10000 なら OFFSET 9999
SELECT /*+ MAX_EXECUTION_TIME(500) */ a, b FROM t FORCE INDEX (`i`)
WHERE a IS NOT NULL ORDER BY a, b LIMIT 1 OFFSET 9999;

-- 途中(? は前の結果)。1 列なら WHERE a > ?
SELECT /*+ MAX_EXECUTION_TIME(500) */ a, b FROM t FORCE INDEX (`i`)
WHERE a > ? OR (a = ? AND b > ?) ORDER BY a, b LIMIT 1 OFFSET 9999;

-- 行が返らなかったら残りを数えて足し、終了。カーソルがまだなければ WHERE a IS NOT NULL
SELECT /*+ MAX_EXECUTION_TIME(500) */ COUNT(*) FROM t FORCE INDEX (`i`)
WHERE a > ? OR (a = ? AND b > ?);
```

**形 B: カーソルが一意にならない**(主キーがなく、索引が非ユニークまたは NULL 可)。同じ値がステップの境界をまたぐので、**`N` ではなく、範囲の `COUNT` の結果を足します**。

```sql
-- 上端を得る。最初は WHERE a IS NOT NULL
SELECT /*+ MAX_EXECUTION_TIME(500) */ a FROM t FORCE INDEX (`k_a`)
WHERE a > ? ORDER BY a LIMIT 1 OFFSET 9999;

-- 行が返ったら、前の上端から今の上端までを数えて足す。最初は WHERE a IS NOT NULL AND a <= ?
SELECT /*+ MAX_EXECUTION_TIME(500) */ COUNT(*) FROM t FORCE INDEX (`k_a`) WHERE a > ? AND a <= ?;

-- 行が返らなかったら残りを数えて足し、終了。上端がまだなければ WHERE a IS NOT NULL
SELECT /*+ MAX_EXECUTION_TIME(500) */ COUNT(*) FROM t FORCE INDEX (`k_a`) WHERE a > ?;
```

3 列以上は同じ形で展開します: `a > ? OR (a = ? AND (b > ? OR (b = ? AND c > ?)))`。パーティションの中で分割するときは、**すべての文に同じ `PARTITION (p)` を付けます**。3 列、4 列の主キー、複合二次索引 + 複合主キー、パーティションごとの合計、サブパーティション、テナントの合計はすべて真の件数と一致しました(全 5 版、`3c-EXP-O2-1-versions-*.json` の `EXP7_designs`)【実測】。

実行の規則:

1. 各文の間に §8 の待ち時間を入れます。
2. **開始の確認**: 2 ステップ目の実カーソルで次の `EXPLAIN` を取り、`access_type=range`、`using_filesort` なし、`used_key_parts` が全列であることを確かめます。**満たさなければ分割しません。** 二次索引 + 主キーの 5 表で条件を満たし、1 万件のステップの `Handler_read_next` は 9,999 でした(`10-EXP-O2-1-all-tables.json` の `secondary_plus_pk_plan_rule`)【実測】。

   ```sql
   SET SESSION explain_json_format_version = 1;   -- 9.7 以降の既定は 2 で形が違う(§2)
   EXPLAIN FORMAT=JSON SELECT a, b FROM t FORCE INDEX (`i`)
   WHERE a > ? OR (a = ? AND b > ?) ORDER BY a, b LIMIT 1 OFFSET 9999;
   ```

3. **カーソルの確認**: NULL が返ったら中止します(ゼロ日付の変換を含む)。前回と同じ値が返っても中止します。サーバーの `>` が前進を保証するのは、送った値が元の値と同じときだけだからです。

   - **文字列などの数値以外のキー**: 各ステップの後で、値が戻ることと、前のカーソルより先へ進んだことを次の文で確かめ、1 行も返らなければ中止します。比較はサーバーに任せます。クライアントの文字列比較は照合順序と一致しないからです。境界の行が直前に削除された場合も中止になりますが、誤った合計を返す方向ではありません。削除を混ぜた歩行 5 回(1,000 ステップで各 44〜45 件の削除文)では中止は 0 回で、低い率でしか試していません(`3c-EXP-O2-1-versions-*.json`)。逆行させたカーソルはこの確認で止まり、確認なしの対照は止まりませんでした(`3a-EXP-O6-LOOP-RULES.json`)【実測】。

     ```sql
     -- 1 ステップ目
     SELECT /*+ MAX_EXECUTION_TIME(500) */ 1 FROM t FORCE INDEX (`i`) WHERE a = ? AND b = ? LIMIT 1;
     -- 2 ステップ目から。新しい値と、前のカーソルの値を渡す
     SELECT /*+ MAX_EXECUTION_TIME(500) */ 1 FROM t FORCE INDEX (`i`)
     WHERE a = ? AND b = ? AND (a > ? OR (a = ? AND (b > ?))) LIMIT 1;
     ```

   - **整数と DECIMAL のキー**: 新しい値が前の値より大きいことをジョブ自身で確かめ、そうでなければ中止します。受信、保存、再送のすべてで、64 ビット整数、BigInt、任意精度の decimal のような無損失の型を使います。double に変換するクライアント(JavaScript の `Number` など)は 2^53 を超える整数を丸めます【文書】。丸めた値が別の既存行を指すと、**エラーなしで合計がずれます**。double を通した BIGINT は 2,000 行を 1,750 行と数え、DECIMAL は前進しなくなって止まりました。直接の整数と、DECIMAL のリテラルや文字列は正しく、下の確認は無損失で 1、double を通すと 0 でした(全 5 版、`3c-EXP-O2-1-versions-*.json`)【実測】。開始前に、キーの最大値と同じ桁の値で往復を確かめ、チェックポイントや JSON を経由するならその経路でも確かめます。0 なら開始しません。

     ```sql
     SELECT 9007199254740993 AS probe;                    -- 受け取る。符号なしキーなら 18446744073709551615
     SELECT CAST(? AS CHAR) = '9007199254740993' AS ok;   -- 受け取った値をそのまま ? に渡す。1 のこと
     ```

4. **ジョブの上限**: 読み進めた行数と実行時間の上限を最初に決めます。行数は概数の 3 倍程度、時間はサービスが許す長さです。超えたら止めます。ステップ数で上限を決めないでください。幅を半分にするとステップが増えるので、`bench/countlib.py` のステップ数の上限(概数 ÷ 開始の幅の 3 倍)は、幅が 156〜1,250 に縮んだ負荷で 2000 万行中 928 万〜1,939 万行のところで止めました(`06`, `08-*.json`)【実測】。止まり方は安全ですが、完走できたはずの歩行も止めた可能性があります。行数の上限は `split_count` の `max_rows` に実装しました。再試験は結果待ちなので、§3 の完走数は暫定です(`0e`, `0f-EXP-O10-ROW-CEILING`、§11)。カーソルが戻る不具合は合計を増やすか、終わらないループになるからです【推論】。同じ理由で何度も止まる(無関係な時間帯の DDL が続くなど)ときは、3 回で打ち切り、運用で時間帯を調整します(判断値)。

## 3. 方法の比較(1 億行、8.4.13)

**時間**: 同じ負荷の中で、順序を入れ替えて各 6 回です。`cold` は別の表(`t_repl`, `t_composite`)の全件読みの直後で、**バッファプールが完全に入れ替わったことは確かめていません**。全件読みは LRU の古い側に留まるので一部の追い出しと考えてください【推論】。cold と warm のディスク読みはほぼ同じでした(`21-EXP-R8-a.json`, `22-EXP-R8-b.json`)【実測】。基準は事前に決めました: 中央値が 20% 以上低く、最速と最遅の範囲が重ならないときだけ速いと呼びます。

## 4. 事前診断

使うのはメタデータと `EXPLAIN` だけで、行は数えません。`EXPLAIN` も短い MDL を取るので、先に SQL 0 を実行します。保留中の DDL があると `EXPLAIN` も待たされ、`lock_wait_timeout` で 1205 になります(全バージョン、`matrix_*.json` の `mdl.explain_during_pending_ddl`)【実測】。

| 確認すること | 取り方 | 方法への影響 |
|---|---|---|
| ビューか | `TABLE_TYPE` | 数える対象を決め直す |
| エンジン | `ENGINE` | InnoDB 以外は §6 |
| パーティションか | `CREATE_OPTIONS` に `partitioned` | パーティションごとに数える |
| 分割に使える索引 | SQL 3 | なければ「分割できないとき」 |
| 既定プランの索引 | `EXPLAIN` の `key` | 1 文で読む索引 |
| 実行中の DDL、長いトランザクション、バックアップ | §8 の SQL、運用予定 | 待つ。始めない |
| 分離レベル、autocommit、接続先 | SQL 0 | 想定外なら開始しない |
| 親子の外部キー | §5 の SQL | 親の DDL も待たせる |
| 表の世代 | §8 の `TABLE_ID` | 終了時に比較する |

`bench/count_preflight.py` は検証環境でこの確認を行い、全 58 表で実行しました。サイズの閾値を使わず、SQL 3 の条件と実カーソルの `EXPLAIN` で判定します(`10-EXP-O2-1-all-tables.json` の `preflight`)【実測】。

| 分からないこと | 根拠 |
|---|---|

| **索引名だけでは実体が分からない** | `t_uniq_notnull` の `uk_code` はクラスタ索引に昇格しており(`INDEX_LENGTH`=0)、`Handler_read_next`=0 です【実測: 同上】 |

実際に読んだ量は、1 ステップ実行して差分で確かめます(`FLUSH STATUS` の権限は不要)。

```sql
SHOW SESSION STATUS LIKE 'Handler_read%';   -- 前
-- 1 ステップ実行
SHOW SESSION STATUS LIKE 'Handler_read%';   -- 後
```

`Handler_read_next` だけでなく、降順走査の `Handler_read_prev`、ソート時の `Handler_read_rnd_next` なども見ます。差が幅の数倍以上なら止めます。`PRIMARY` の全件 `COUNT(*)` は `Handler_read_next` が 0 なので、この確認は使えません。

### 概数の精度

**`TABLE_ROWS`=0 の原因は統計キャッシュでした。** 空の間に読むと 0 がキャッシュされ、100 万行入れて 30 秒後も既定の設定では 0 のままです。`expiry=0` なら 998,490、一度も読まずに投入した表は既定でも 998,490 でした。実表の `d_soft_delete` などでも同じで、`expiry=0` のセッションで読んでも、他のセッションのキャッシュは 0 のままです(`24-EXP-R10.json`)【実測】。

大量変更の後の誤差(%、100 万行の表、`24-EXP-R10.json`)【実測】:

| 変更 | 既定の `TABLE_ROWS`(キャッシュ) | `expiry=0` / `EXPLAIN` / `NUM_ROWS` 直後 | 同 20 秒後 | `ANALYZE` 後 |
|---|---|---|---|---|
| 一様に 50% 削除 | +98.29 | -1.71 | -0.84 | -0.84 |
| 先頭 50% 削除 | +98.29 | -1.71 | -0.84 | -0.84 |
| 90% 削除 | **+891.46** | -8.54 | -0.82 | -0.82 |
| 半数更新 | -0.85 | -0.85 | -0.85 | -0.85 |
| 2 倍に追加 | -50.43 | -0.43 | -0.87 | -0.87 |
| 50% 削除、`STATS_AUTO_RECALC=0` | +98.29 | -1.71 | -1.71 | -0.84 |
| 50% 削除、**`STATS_PERSISTENT=0`** | +100.03 | **+94.19** | **+94.19** | +0.03 |

- **SQL 1 の `expiry=0` を必ず付けます。** 既定のままだと桁違いにずれます。
- 上の表の `ANALYZE` は精度を示すためのものです。カウントの最中の `ANALYZE TABLE` は、8.4.13、9.7.4、26.10.0 で 3 回ずつ試し、PENDING も待ち状態も出ず、8.4.13 では 3.6〜6.6 ms で終わりました(`59-EXP-O6-ANALYZE-*.json`)【実測】。カウントは最長でも 1.17 秒(9.7.4 の 1 回)と短く、これより長い場合と、マニュアルのスレッド状態の説明にある `Waiting for table flush` との関係は未確認です。
- `mysql.innodb_table_stats.n_rows` は再計算まで古い値です(50% 削除の直後で +98.29%)。
- `STATS_PERSISTENT=0` の表は `EXPLAIN` も `expiry=0` も大きくずれ、`ANALYZE` まで直りません。`CREATE_OPTIONS` で確かめ、該当すれば概数に使わないでください。
- **下の誤差を上限と考えないでください。** 投入直後の静かな表でも `t_composite` は 12.15% ずれました(`count_shapes.json`)。
- `MAX-MIN+1` は `t_sparse` で 10,009,600%、`d_snowflake` で 15,518,909,181% ずれます(`count_shapes.json`)。
- 時間は `EXPLAIN` 0.105 ms、`TABLE_ROWS` 0.194 ms、`INNODB_TABLESTATS` 0.205 ms、`innodb_table_stats` 0.044 ms です。パーティション表は `PARTITIONS.TABLE_ROWS` の合計が 666,324(実数 666,700)で、`INNODB_TABLESTATS` では `NAME` の検索に何も一致しませんでした(`24-EXP-R10.json`)。

### 実行中の再確認

統計や索引が変わると、プランも変わります。`FORCE INDEX` は索引の選択を固定しますが、次は残ります【推論、未計測】。

- 実行中に索引が削除または不可視化されると文がエラーになります。カーソルを保存せず止め、§4 からやり直します。
- 1000 ステップごとに、現在のカーソル値で `EXPLAIN` を取り直し、`key`、`used_key_parts`、`Using filesort` の有無を確かめます。
- ステップ時間が中央値の数倍に増えたら、待ちを増やすか止めます。

## 5. ロック

### 文の形と分離レベル

トランザクション内で各文を実行した後に残るレコードロック数です。20 万行で確認しました(`lock_factors.json`, `40-EXP-R11.json`、8.4.13)【実測】。形ごとの結果は主キーのみ、主キー + 二次索引、索引なしの 3 設計で同じでした(ロック数は設計で変わります)。

| 文 | READ UNCOMMITTED / READ COMMITTED | REPEATABLE READ(既定) | SERIALIZABLE(トランザクション内) |
|---|---|---|---|
| **`SELECT COUNT(*)`** | **0** | **0** | 全行 + ギャップ |
| `SELECT COUNT(*) INTO @c` | 0 | 0 | 全行 + ギャップ |
| 派生表、CTE、スカラー副問い合わせ、`SELECT @x := ...` | 0 | 0 | 全行 + ギャップ |
| `EXPLAIN ANALYZE`、`PREPARE` した `SELECT` | 0 | 0 | 全行 + ギャップ |
| `CALL` の中の `SELECT`、`SELECT ... INTO` ローカル変数、ストアド関数 | 0 | 0 | 全行 + ギャップ |
| `FOR SHARE` / `FOR UPDATE` / `LOCK IN SHARE MODE` | 全行 | 全行 + ギャップ | 全行 + ギャップ |
| **`SET @c = (...)`、`DO (...)`、`PREPARE` した `SET`、`CALL` の中の `SET`、トリガーの中の `SET`** | **全行** | 全行 + ギャップ | 全行 + ギャップ |
| `INSERT..SELECT`, `REPLACE..SELECT`, `UPDATE..(SELECT)`, `CREATE TEMPORARY TABLE..SELECT` | 0 | 全行 + ギャップ | 全行 + ギャップ |

- 永続表の `CREATE TABLE ... AS SELECT` は判定できません。暗黙コミットで文の後に 0 件になり、実行中のピークも取れませんでした(下記)。形として避けます【実測】。
- 0 の形を許可する理由にはしません。カウント専用クライアントの直接の `SELECT` に限るのは、ヒントが効くのがその形だけだからです(§1)。
- ラボの `binlog_format` は ROW です。STATEMENT は【未計測】です。
- SERIALIZABLE でも **autocommit の 1 文は読み取りロックなし**です【文書】。実行中の観測では行ロック待ち 0、ピーク行ロック 6(`impact_lock_serializable_autocommit.json`)、何もしない状態は 8(`impact_lock_baseline.json`)でした【実測】。

500 万行の `t_hot` で各文を繰り返したときのサービス側の影響です(`impact_lock_*.json`)【実測】。繰り返しによる飽和を含むので、1 回の文の害そのものではありません。

| 実験 | 書き込み p50 前→中 ms | 最大 ms | 行ロック待ち |
|---|---|---|---|
| 何もしない | 1.63→2.08 | 314.22 | 0 |
| `SELECT COUNT(*)` | 1.35→2.51 | 271.31 | 0 |
| SERIALIZABLE, autocommit | 1.85→1.63 | 174.89 | 0 |
| `INSERT..SELECT` READ COMMITTED | 1.5→1.58 | 240.4 | 0 |
| `INSERT..SELECT` REPEATABLE READ | 1.69→**13344.87** | 27374.94 | 224 |
| `SET @c=(...)` REPEATABLE READ | 2.74→**13776.27** | 25017.12 | 254 |
| `FOR SHARE` | 3.28→**13150.17** | 26537.49 | 198 |
| SERIALIZABLE, トランザクション内 | 1.67→**12262.98** | 24632.87 | 262 |
| `LOCK TABLES t READ` | 1.31→**337.8** | 1577.18 | 0(MDL 待ち最大 4) |

`data_locks` を毎秒読むサンプラーは、この遅延の主因ではありません。同じロック文で交互に 3 回比べ、書き込み p50 はサンプラーあり 5526.67〜8475.89 ms、なし 7055.55〜8806.03 ms で重なりました(`50-EXP-SOL-11.json`)【実測】。

### 索引とデータで変わること

同じ文でも、ロックされる索引と止まる書き込みは設計で変わります(`lock_factors.json`, `40-EXP-R11.json`、REPEATABLE READ)【実測】。

| 設計 | `FOR SHARE` の行ロック | `FOR UPDATE` の行ロック | 非索引列の UPDATE | 索引列の UPDATE | INSERT |
|---|---|---|---|---|---|
| 主キーのみ | 200,455 | 200,455 | 止まる | - | 止まる |
| 主キー + 小さい二次索引 | 200,304(二次索引のみ) | 400,304(両方) | `FOR SHARE` なら**通る** | **止まる**(1205) | 止まる |
| 主キーも索引もなし | 200,533 | 200,533 | 止まる | - | 止まる |

- どの索引を読むかは統計で変わるので、ロックする形を「この設計なら安全」とは言えません。
- READ COMMITTED 以下では INSERT は止まりませんが、既存行のレコードロックは残ります。
- 通常の `SELECT` では NULL、同値、型の問題が行ロックを増やすことはありません。ただし文が長くなり、MDL と undo の保持を伸ばします(§1 の SQL 3 と時間上限で防ぎます)【推論】。

### ジョブが全行ロックしていないかを見つける

**実行前**: EXPLAIN では分かりません。複数行にまたがる SQL も探します。

```bash
rg -U -i '(insert|replace|update|set|create|do)\b[^;]*count\s*\(|count\s*\([^;]*for\s+(share|update)|lock\s+tables' <ジョブのコード>
```

同じ正規表現を 10 個の例に適用し、ロックする形 6 個と ORM 風の 1 個を検出し、通常の `SELECT` 2 個を誤検出しませんでした。`;` をまたぐ例は検出しません(`12-EXP-6.json` の `job_code_search`)。`rg` 自体はコンテナになく【未実行】です【実測】。

```sql
-- コードの外にある文。sys スキーマの結果は無視してよい(`12-EXP-6.json`)
SELECT ROUTINE_SCHEMA, ROUTINE_NAME FROM information_schema.ROUTINES WHERE ROUTINE_DEFINITION LIKE '%COUNT(%';
SELECT TRIGGER_SCHEMA, TRIGGER_NAME FROM information_schema.TRIGGERS WHERE ACTION_STATEMENT LIKE '%COUNT(%';
SELECT EVENT_SCHEMA, EVENT_NAME FROM information_schema.EVENTS WHERE EVENT_DEFINITION LIKE '%COUNT(%';
```

パターン検索では網羅できないので、ORM やバッチツールの文はステージングで実際に流して確かめます。

**実行中**:

```sql
SELECT trx_mysql_thread_id, trx_isolation_level, trx_rows_locked, trx_lock_structs,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_s, LEFT(trx_query, 120) AS q
FROM information_schema.INNODB_TRX WHERE trx_rows_locked > 1000 ORDER BY trx_rows_locked DESC;
```

**短い文はこの監視をすり抜けます。** 20 万行をロックする文は数十 ms で終わり(`DO` の形で 19〜40 ms)、5 ms 間隔で読むと 204 回中 203 回でピーク 0、残る 1 回も 37 でした。文の後に残るロックは `data_locks` で見えました(`40-EXP-R11.json`)【実測】。`data_locks` を全行ロック中に全件数えると重いので、`LIMIT` を付けます。

### MDL の連鎖

長い `COUNT(*)` は行ロックを取りませんが、DDL が来ると**サービス全体を止めます**。

```text
長い COUNT(*) が MDL 共有を保持
 → ALTER TABLE(INSTANT でも)が排他を待つ
 → その後の SELECT / UPDATE がすべて ALTER の後ろに並ぶ
```

開始 5 秒後に `ALGORITHM=INSTANT` の `ALTER` を発行した結果です【実測、各 1 回】。**待ちは 1 文の残り時間です。** この回の 1 文は 18.68 秒で、§3 の再計測(5.72〜6.90 秒)と同じ条件ではありません。同じ時間の文なら待ちは 1〜2 秒になるはずで【推論】、桁ではなく仕組みを読んでください。

| | ALTER の待ち | 読み取り p50 | 書き込み p50 | 書き込み最大 | MDL 待ち |
|---|---|---|---|---|---|
| 長い `COUNT(*)`(`impact_mdl_long_count_then_ddl.json`) | **13.74 秒** | **4607.03 ms** | **5819.68 ms** | 13732.47 ms | 9 |
| 分割(`impact_mdl_split_count_then_ddl.json`) | **0.02 秒** | 1.22 ms | 2.17 ms | 278.33 ms | 0 |

**分割の待ちは ALTER が当たる位置で変わり、おおよそ「ステップ 1 つ分 + DDL 自体の時間」です**(`43-EXP-SOL-12.json`)【実測】。

| ALTER | 静かなとき ms | ステップの開始直後 ms | ステップの途中 ms | 待ちの間 ms |
|---|---|---|---|---|
| INSTANT の時間 | 21.5〜49.8 | 79.4〜141.3(3 回) | 40.4〜48.1(3 回) | 15.0, 44.0(2 回) |
| 同じ時間の別の読み取りの最大 | - | 73.0〜135.2 | 34.6〜39.2 | 11.6, 37.9 |
| INPLACE の時間 | 2,693.1〜2,783.6 | 2,670.4〜2,869.9(5 回) | 2,481.9〜4,050.9(5 回) | 2,503.4〜3,745.3(5 回) |
| 同じ時間の別の読み取りの最大 | - | 62.0〜73.8 | 25.4〜30.1 | 3.1〜7.5 |

INSTANT は同じ表で回数を重ねると 4092 になり(INSTANT の列追加の回数上限と考えられる【推論】)、残りの試行は無効です。この実験のステップ最長は INSTANT で 72.86〜146.32 ms、INPLACE で 137.58〜299.69 ms です。INPLACE の時間の大半は DDL 自体の作業で、カウントが足す待ちはステップ 1 つ分と同じ桁です。

対策:

- 分割がステップの間に MDL を手放すのは、autocommit で既存トランザクションがないときだけです(SQL 0)。
- 1 文で走らせるなら DDL の予定を確認し、時間上限を付けます。
- 上限を付けた文は、保留中の DDL の後ろに長く並びません。1205 か時間切れで返ります(§1)。
- DDL 側にも短い `lock_wait_timeout` を設定します【推論】。
- 対象テーブルへの MDL 待ちを見つけたら、すぐカウントを止めます(§8)。

**バックアップの FLUSH**: 長い `COUNT(*)` が実行中だと、`FLUSH TABLES` はカウントの終わりまで待ち、その表への読み取りが後ろに並びます。別の表の読み書きは止まりません(`41-EXP-R12.json`)【実測】。

| | FLUSH の待ち | 対象表の読み取り最大 | 別の表の書き込み最大 | 見えた監視 |
|---|---|---|---|---|
| 長い `COUNT(*)` + `FLUSH TABLES` | 5011.48 ms | **4949.7 ms** | 5.8 ms | `Waiting for table flush`。**MDL の PENDING は 0 件** |
| 長い `COUNT(*)` + `FTWRL` | 5408.79 ms | 5356.4 ms | 8369.9 ms | state と MDL の `GLOBAL` |
| 分割 + `FLUSH TABLES` | 7.16 ms | 0.3 ms | 1.4 ms | 一瞬の state のみ |
| 分割 + `FTWRL` | 0.39 ms | 10.7 ms | 6682.9 ms(FTWRL を保持している間) | state と MDL の `GLOBAL` |

**`metadata_locks` だけでは FLUSH の連鎖を検知できません。** state も監視します(§8)。カウントを KILL すると FLUSH はすぐ通りました(2.0 秒で KILL、FLUSH も 2.0 秒)。

### 外部キー

- **読み取りの `COUNT(*)` が親子に行ロックを取るという証拠はありません。** 外部キーの検査が走るのは書き込みです【文書】。
- **子を数えている間、親の `ALTER` は待ちます。その間は親と子の読み書きが並びます。** 子の読み取りを保持すると、親への INSTANT も INPLACE も 1 秒で 1205 になりました。親を読んでいても祖父母の `ALTER` は待ちますが、子を読んでいるときの祖父母の `ALTER` は通りました(1 段だけ)。実際の長いカウントでも、親の `ALTER` はカウントの終わりまで 2,272.78 ms 待ちました(`42-EXP-4.json`)【実測】。**DDL の予定は親子まとめて確認します。**
- 親の `ALTER` が待っている間は、親と子の読み取り、子の書き込みが 1205 になり、祖父母と無関係の表は通りました。`metadata_locks` では子の `EXCLUSIVE`, `PENDING` として見えるので、対象表の監視で検知できます(同)【実測】。
- `LOCK TABLES` の及ぶ範囲です(同)【実測】。

| 発行 | 止まるもの(1205) | 通るもの |
|---|---|---|
| 子 `READ` | 子の書き込み | 親の読み書き、祖父母 |
| 親 `READ` | 親の更新 | 子の読み書き、祖父母 |
| 子 `WRITE` | 子の読み書き、**親の更新** | 親の読み取り、祖父母 |
| 親 `WRITE` | 親と子の読み書き、**祖父母の更新** | 祖父母の読み取り |
| 祖父母 `WRITE` | 祖父母の読み書き、**親の更新** | 親の読み取り、子の読み書き |

- `LOCK TABLES order_items READ` を繰り返すと、2 段上の親 `customers` への書き込み p99 が 24.84→1093.7 ms になりました(`impact_fk_lock_tables_child_blocks_parent.json`)。行ロック待ち 0、`customers` の MDL 排他 0 で、テーブルロックの証拠はありません。スキャンの I/O と考えられます【推論】。

```sql
SELECT TABLE_SCHEMA, TABLE_NAME, COLUMN_NAME, REFERENCED_TABLE_SCHEMA, REFERENCED_TABLE_NAME
FROM information_schema.KEY_COLUMN_USAGE
WHERE REFERENCED_TABLE_NAME IS NOT NULL
  AND ((TABLE_SCHEMA='db' AND TABLE_NAME='t') OR (REFERENCED_TABLE_SCHEMA='db' AND REFERENCED_TABLE_NAME='t'));
```

### 実行中のカウントを止める

| 方法 | 実測 |
|---|---|
| `KILL QUERY <id>` | 送信から数 ms で 1317(上限 5 秒に対し 1 秒で送信、1003.5〜1012.2 ms で返った、`13-EXP-O2-2.json`) |
| `MAX_EXECUTION_TIME` | 上限で返った。1317 または 3024(§1) |
| 分割 | 次のステップを実行しない(`13-EXP-O2-2.json` の `stop_flag_with_pending_ddl`) |

読み取りのみなので巻き戻しはありません【推論】。

**ドライバの読み取りタイムアウトは停止ではありません。旧reqmix2のprobeはKILL後の終了確認が不足するため、以下のKILL後の値を後始末完了の根拠にしません（SOL-PROTOCOL-003）。** クライアントが 5 秒で 2013 を受けた後も、サーバーの文は MDL を持ったまま、観測を終えた 24 秒時点でも実行中でした。`KILL` すると 0.2 / 0.4 秒で消えました(`06`, `08-*.json` の `client_timeout`)【実測】。保留中の `ALTER` はそのまま並び、ジョブは止めたつもりになります。止めるのは `KILL` かサーバー側の上限です。

## 6. テーブル設計カタログ

出典はすべて `10-EXP-O2-1-all-tables.json` の静かなサーバーの結果です【実測】。

- **値の形式**: 1 文(SQL 2)ms / 手順全体の秒 / 最長の文 ms。幅は 1 万、文の上限は 500 ms で、本文の手順そのものです。手順全体の秒は NULL の `COUNT` と確認の文を含みます。
- 分割の結果は、対象の **51 表すべてで `COUNT(*)` と一致**しました。分割しないのは手順どおりの 7 表です(`d_enum_pk`, `d_prefix_unique`, `d_noindex`, `t_myisam`, `t_memory`, `t_archive`, ビュー)。一致は書き込みのない状態での確認です。
- 推奨は特に記載がなければ §1 のフローです。「分割不可」は「分割できないとき」へ進みます。

## 7. 実行時の状態と「一瞬の値」

### 分割の合計の誤差

**分割の合計は、ある一瞬の件数ではありません。** 100 万行の表に書き込みながら、幅 1,000 で各 1 回数えました。変更はどれも約 11 秒間に 1,540〜1,787 件です(`23-EXP-R5.json`)【実測】。

| 変更 | カーソルの索引 | 合計 − 終了時の実数 | % | 変更 1 件あたり |
|---|---|---|---|---|
| 件数が変わらない列の更新 | `PRIMARY`, `k` | 0 | 0 | 0 |
| まだ読んでいない範囲への追加(`insert_ahead`) | `PRIMARY`, `k` | 0 | 0 | 0 |
| 読み終えた範囲への追加(`insert_behind`) | `PRIMARY` / `k` | -1,584 / -1,531 | -0.158 / -0.153 | **-0.994** |
| 一様な削除 | `PRIMARY` / `k` | +833 / +816 | +0.083 / +0.082 | +0.50 |
| カーソルの索引列を増やす更新(`update_k_forward`) | `k` | +834 | +0.083 | +0.51 |
| カーソルの索引列を減らす更新(`update_k_backward`) | `k` | -788 | -0.079 | -0.48 |
| 主キーの更新 | `PRIMARY` | +770 | +0.077 | +0.49 |
| 別の索引の列を動かす更新 | `PRIMARY` / `k` | 0 | 0 | 0 |

- 合計は、コミット順と境界から予測した値と一致しました(14 回中 13 回で差 0、1 回で差 1)。**誤差の仕組みは説明どおりです。**
- **どの回も誤差の絶対値は実行中の変更数以下でした。** この上限は、この表への変更数が分かっている実験での話です。一般のサーバーで `Innodb_rows_inserted/deleted/updated` の増分を使うと、サーバー全体の値なので広すぎる目安になり、ウォーク前に変更してウォーク中にコミットした長いトランザクションは数え損ないます【推論】。厳密な上限として使わないでください。ロールバックや長いトランザクションは未計測です。
- **次の旧reqmix2の数値を静止真値・drift上限の根拠にする主張は撤回します。未完了writeとサーバー処理終了の確認が不足しています（SOL-PROTOCOL-003）。旧表示値として保持します。** 2000万行の旧比較では分割PRIMARYの差を次のように報告しました。散らばる書き込みで 78 / 352 文(毎秒 100)、1,808 / 7,002 文(毎秒 800)、追記と削除で 274 / 544 文、2,015 / 4,019 文です(`07`, `08`, `09`, `09a-*.json` の `drift`)【実測、各 1 回】。
- **照合や課金には次の方法か書き込み停止中の値を使ってください。**

### 一瞬の値が必要なとき

SQL 0 のセッション上限は、この節の 1 文も止めます。ヒントで上限を明示してください(§1)。上限は DDL とサービスの都合で決める判断値で、打ち切られたら §1 のエラーの表に従います。

```sql
SELECT /*+ MAX_EXECUTION_TIME(60000) */ COUNT(*) FROM t;
```

**延長の条件**: 1 文の上限を延ばすのは、次をすべて満たすときだけです。

- DDL とバックアップがないと運用で確認している。
- 上限は外しません。書き込みが数える索引のあちこちに当たる表で二次索引の 1 文が打ち切られたら、同じ短い上限で `FORCE INDEX (PRIMARY)` を一度試し、完走したほうを使います。どちらも打ち切られたら延ばさず、分割かレプリカへ進みます。2000万行・毎秒800文の旧報告は原因分類と終了確認を再監査中で、確認済み上限の反復とは扱いません（§3/14）。**ほかの大きさと速度では `PRIMARY` が速いとは言えません。** `PRIMARY` という名前の索引がない表(主キーなし、昇格した NOT NULL ユニーク)にこの形は使えず、1176 になると考えられます【推論、確認は結果待ち、§11】。`IGNORE INDEX` で読む形も結果待ちで、それまでは分割かレプリカへ進みます。
- 予想所要時間が、サービスが許す undo の滞留時間より短い。予想は過去の同条件の実績など根拠がある場合に限ります。打ち切られたCOUNTから進捗率や残時間を一般には推定できません。根拠がなければ延長せず、primary以外の経路も検討します。
- 監視の接続が動いており、HLL が許容値を超えたら止める(§8)。**この文自身の読み取りビューが purge を止めます。**
- 長くかかるなら primary の 1 文にせず、分割か専用のレプリカを選びます。

**読み取りビューを長く持つと HLL は書き込み速度に比例して増えます。** ビューを 60、180、300 秒持つと、毎秒 100 文で 6,018 / 18,046 / 30,070、毎秒 400 文で 24,034 / 72,077 / 120,099 でした(`3g`, `3h-EXP-O6-LONG-UNDO-*.json`)。1 つのスナップショットで代用しており、カウントの文ではありません。この範囲では次のとおりです【実測】。

- 保持中の書き込み p50 は低 1.28〜1.76 ms、高 0.86〜0.92 ms で増えず、p99 は 15.48〜31.87 ms で、ビューなしの回(25.84, 25.1 ms)と同程度です。新しいビューのカウントも 0.1〜0.128 秒で変わりません。
- 解放の後 1 秒以内に HLL は元に戻り、undo ファイルの大きさは変わりませんでした。高負荷の 180 / 300 秒の解放直後は書き込み p95 が 23.04 / 39.43 ms(60 秒では 1.96 ms)に上がりました(各 1 回)。
- **これは点 `UPDATE` だけの結果で、安全時間の根拠にはなりません。** HLL はトランザクション数で undo の容量ではありません。1 トランザクションで 300 万行を更新しても HLL は 34 のままで(`51-EXP-3.json`)、読む側の負担は下記のとおり大きくなります。数時間と、大きいトランザクションの滞留は【未計測】です。

| 方法 | 得られる時点 | 代償 | 根拠 |
|---|---|---|---|
| autocommit の 1 文の `COUNT(*)`(RR / RC) | 文の最初の整合性読み取りの時点 | 実行中は MDL を保持し undo が滞留(§3, §5) | 【実測・文書】 |
| レプリカの適用を止める(`STOP REPLICA SQL_THREAD`)、`@@gtid_executed` を記録、数えて再開 | その GTID 位置 | 意図した遅延。止めたレプリカに読みを向けない。フィルターがあれば primary の件数ではない | 下記【実測】 |
| バックアップやクローンの複製 | 取得時点 | 準備の時間とストレージ | 【未計測】 |
| `START TRANSACTION WITH CONSISTENT SNAPSHOT` のあと分割 | 開始時点 | MDL も undo も終了まで保持するので分割の利点が消える。**推奨しない** | 【推論】 |

**レプリカの手順**(2000 万行、3 回、`25-EXP-R15.json`)【実測】: 停止は 4 ms、カウント 1.02〜5.62 秒、件数は適用済みの行数と一致し(3 回とも)、カウントの間 GTID は変わらず、再開後の追いつきは 1.01〜1.03 秒でした。その間 primary には 223〜393 行が書かれています。**記録した GTID 位置は primary の記録と対応しました**(3 回とも、最大 ID 30,000,115 など)。フィルターで `t_dense` はレプリカに存在せず 1146 になりました。**レプリカに対象表があることを先に確かめます。**

**この手順は通常のチャネル 1 つのレプリカに限ります。** `SHOW REPLICA STATUS` は全行を見ます。2 行以上あれば、何も変更する前に手順をやめます。チャネルを指定しない `STOP REPLICA` と `START REPLICA` はすべてのチャネルに作用し、運用で止めているチャネルまで開始します【文書】。Group Replication のチャネルも対象外です。2 チャネルで手順は何も変更せず拒否し、チャネルを指定しない `START` は止めてあったチャネルの適用を動かしました(`03-EXP-S8-REPLICA-CHANNEL-GATE.json`)【実測】。

**止めた適用は、失敗しても自分で戻します。** カウントが時間切れ、`KILL`、接続断のどれで失敗しても、§1 の「止まる」はジョブの話で、レプリカを止めたままにしません。

- 開始前に `Replica_SQL_Running` を記録します。**`STOP` を送る前に「止めようとした」と記録します。** `STOP` が失敗しても、停止の要求は生きていて後から止まるからです。`rpl_stop_replica_timeout` で 1875 が返った直後は `Yes` のまま、2.5 秒後に `No` になり、以前の手順では止まったまま残りました。`STOP` の接続を切っても 1.5 秒後に `No` になりました。**`STOP` が失敗したら状態を見続け、止まるのを見てから開始します。動いていることは、戻った証拠になりません。** 停止の要求がまだ効いていないだけかもしれないからです。止まるのを見ないまま期限が来たら「未確認」として人に知らせ、見続ける役目を誰かに引き継ぎます。この規則は `restore_applier` に実装しました。以前の実装は、ロックを 4 秒で解放した試験で `STOP` が失敗した回を 12.09 秒で元に戻しましたが(`02-EXP-S8-REPLICA-STOP-FAILURE.json`)【実測】、期限より長く続く場合は止まっていないのに復旧と報告する作りでした。期限を超える試験も正常終了しました(`0c-EXP-S8-REPLICA-STOP-LONG.json`)。旧実装は復旧済みと報告してから14.2秒後に停止しました。修正版は15秒の期限では2回とも未確認を返し、引継ぎ後に停止を観測して再開、GTID追いつきまで確認しました。60秒の期限でも2回とも停止を観測して再開しました。元から停止中の負対照を勝手に再開せず、最終状態とデータ復元も確認しました。
- **自分が止めようとしたときだけ** `START REPLICA SQL_THREAD FOR CHANNEL ''` を、**カウントとは別の接続で**実行します。もともと止まっていたものは開始しません。
- 再開後に `SHOW REPLICA STATUS` と `WAIT_FOR_EXECUTED_GTID_SET` で追いつきを確かめ、それから読み先に戻します。戻ったと確かめられなければ、人に知らせます。失敗したカウントの値は使いません。
- `STOP` が成功した後のカウントの失敗は、上限切れ、`KILL`、接続断の 3 通りとも適用は再開して追いつき、自分が止めていない場合は止まったままでした(`3i-EXP-S6-REPLICA-FAILURE-CLEANUP.json`、修正前の実装)【実測】。ジョブのプロセス自体が落ちた場合は再開する主体がいないので、外部の監視で `Replica_SQL_Running` を見ます【推論】。HA の昇格候補から外す扱いと、長い停止での relay log の容量は【未計測】です。

primary の読み取りを避ける効果です。2000 万行、各 1 回で、初回の実験群の値です【実測】。**レプリカで実行しても primary の書き込み p50 は 4.22 ms で、直前の 2.06 ms と対照の 2.0 ms より高いままです。** レプリカと primary は同じ VM を共有しており(§2)、物理的に分離した効果はこのラボでは示せません。

### 停止条件

監視はジョブのステップと**別の接続とスレッド**で動かします。ステップが長引いている間にも判定します。

- **止めるときは、先に共有の停止フラグを立ててから `KILL QUERY` します。** ジョブは文の発行前と例外時にフラグを確認し、立っていれば再試行しません。MDL 待ちからの一連の停止を実測しました(§1 のエラーの表)。
- **監視の文が失敗した、計装が無効になった、監視の接続が切れたときも止めます。** 計装は開始時だけでなく**監視の周期ごとに読み直します。** 無効になっても `metadata_locks` は空のまま成功するからです。開始後に無効化すると、読み直さない以前の監視は 30 万行を最後まで数えて気づかず、今の監視は 3 回とも 21〜22 ステップで止まりました(`3b-EXP-6-monitor.json`)。開始時に無効なら拒否し、待機一覧が空でも 20 万行を最後まで数えて誤った停止はありませんでした(`45-EXP-SOL-6.json`)。無関係な表への DDL の待ちで止まらず、`FLUSH` では止まることも確かめました(`3b-EXP-6-monitor.json`)【実測】。**ただし権限の喪失はこの方法では分かりません。** 実行中に `PROCESS` を取り消しても既存の接続は読み続け、ジョブは止まりませんでした。新しい接続は 1227 です(`44-EXP-R13.json`)【実測】。権限の変更は運用で調整します。
- 閾値は判断値なので、サービスの平常値に合わせてください【推論】。

| 監視項目 | 取り方 | 動作 |
|---|---|---|
| 対象テーブルの MDL 待ち > 0 | `metadata_locks` の `LOCK_STATUS='PENDING'` | **直ちに止める**。再開は競合解消・所有者・累積予算を確認後だけ |
| `Waiting for table flush`, `Waiting for tables`, `Waiting for global read lock` | `performance_schema.threads` の state。`metadata_locks` には出ない場合がある(§5)。サーバー全体の待ちなので表で絞らない。`Waiting for table metadata lock` は含めない(無関係な表の DDL で止まらないように、対象表の PENDING で判定する) | **直ちに止める** |
| ジョブの接続が MDL を持っている | **ジョブ自身が**文を発行していない間に、別の接続で下の SQL。非同期の監視では実行中の文を誤認する | **止める**。SQL 0 の前提が崩れている |
| 行ロックを持つジョブ | §5 の `INNODB_TRX` | すぐ止めて修正 |
| アプリのp95/p99・エラー率、CPU、I/O待ち・帯域・IOPSが所有者の予算を超えた | アプリ・基盤の計測。基準値と回復期間も記録 | 初回試行を含めて止める。p50だけや共通倍率で許可しない |
| ステップ時間が中央値の数倍 | ジョブ自身 | 待ちを増やす。続けば止める |
| `Threads_running` の増加 | `performance_schema.global_status` | 待ちを増やす |
| HLL が許容値を超えた(許容値は平常値から決める判断値) | `INNODB_METRICS` | **止める。** 長い 1 文ならそのジョブ自身が原因。ジョブが短い文なら、ほかの長いトランザクションを探す |
| `Innodb_row_lock_current_waits` > 0 が続く | `global_status` | 文の形を再確認 |
| レプリカ遅延の増加 | `SHOW REPLICA STATUS` | レプリカで実行中なら止める |
| 接続先の変化 | `@@server_uuid`, `@@read_only` | 止めて最初から |

```sql
SELECT OBJECT_SCHEMA, OBJECT_NAME, LOCK_TYPE, LOCK_STATUS, OWNER_THREAD_ID
FROM performance_schema.metadata_locks
WHERE OBJECT_TYPE = 'TABLE' AND OBJECT_SCHEMA = 'db' AND OBJECT_NAME = 't';

SELECT PROCESSLIST_ID, PROCESSLIST_STATE, PROCESSLIST_TIME, LEFT(PROCESSLIST_INFO, 120)
FROM performance_schema.threads
WHERE PROCESSLIST_STATE IN ('Waiting for table flush', 'Waiting for tables', 'Waiting for global read lock');

-- ジョブの接続が文の間に MDL を持っていないか(? はジョブの CONNECTION_ID())
SELECT m.LOCK_TYPE, m.LOCK_STATUS FROM performance_schema.metadata_locks m
JOIN performance_schema.threads t ON t.THREAD_ID = m.OWNER_THREAD_ID
WHERE t.PROCESSLIST_ID = ? AND m.OBJECT_SCHEMA = 'db' AND m.OBJECT_NAME = 't';
```

**`INNODB_TRX` ではジョブの異常を判定できません。** 6 通りの接続状態で比べました(`14-EXP-SOL-1.json`)【実測】。

| 接続の状態 | ジョブの MDL | `INNODB_TRX` | 別の接続の `ALTER` |
|---|---|---|---|
| 新規の接続 | なし | なし | 通る |
| SQL 0 の前に `START TRANSACTION` | **あり** | **なし** | 1205 |
| 同上 + 読み取り | あり | あり | 1205 |
| SERIALIZABLE で同上 | あり | あり(1003 ロック) | 1205(`UPDATE` も) |
| ドライバが autocommit 無効、SQL 0 で解消 | なし | **あり** | 通る |
| SQL 0 の後に autocommit 無効 | **あり** | **なし** | 1205 |

ジョブの MDL は 6 通りすべてで `ALTER` の結果と一致し、`INNODB_TRX` は 3 通りで食い違いました。

### 表の世代と再開

分割は文の間に DDL を通すので、同じ名前のまま中身が入れ替わることがあります。

**分割の間は、`RENAME` の入れ替え、`TRUNCATE`、パーティションの `DROP`/`TRUNCATE`/`EXCHANGE` を実行しないよう運用で調整します。** 調整できないなら、その表の分割の合計を実数として扱わないでください。

次の `TABLE_ID` の比較は補助です。開始時と終了時に比べ、変わっていたり、行が返らなかったりしたら**全体を捨てます**。

```sql
SELECT NAME, TABLE_ID FROM information_schema.INNODB_TABLES WHERE NAME = 'db/t' OR NAME LIKE 'db/t#p#%';
```

| 途中の操作 | 合計 | 開始時 / 終了時の実数 | `TABLE_ID` |
|---|---|---|---|
| `RENAME` で入れ替え | 3 | 3 / 2 | 変わった → 捨てる |
| **入れ替えて元に戻す** | **2** | **3 / 3** | **同じ → 検知できない** |
| パーティション `DROP` | 99 | 150 / 99 | 変わった |
| パーティション `TRUNCATE` | 99 | 150 / 99 | 変わった |
| パーティション `EXCHANGE` | 119 | 150 / 119 | 変わった |

出典は `46-EXP-SOL-7.json`【実測】。**`TABLE_ID` の一致は、途中で何もなかった証拠ではありません。**

**既定は「中断したら最初からやり直す」です。** 再開する場合だけ、カーソル(型を保持)、合計、ステップ番号、`server_uuid`、`TABLE_ID` を 1 件の記録として原子的に保存し、一致を確かめます。結果の保存前に落ちたステップは足しません。再接続したら新しい接続で SQL 0 からやり直します。

- `server_uuid` の確認で、別のサーバーへの再開を拒否できました(`46-EXP-SOL-7.json`)【実測】。
- 確認なしで止めたレプリカに続きを数えると、primary の 20,000,100 に対して 20,000,000 になり、エラーは出ません。差は停止中の 100 行です(同)【実測】。
- 同じサーバーで接続を切って再開すると、1 万 + 1999 万で一致しました(同)【実測】。

## 9. 集計カウンタ(数えない方法)

トリガーやアプリケーションで行数を保持すれば、読むのは 1 行です。頻繁に行数を読むなら検討します。

**競合**: カウンタ 1 行をトリガーで更新すると、INSERT がその行で直列化されます。INSERT 100 件/秒の結果です【実測】。

| | 書き込み p50 前→中 ms | p99 前→中 ms | 行ロック待ち |
|---|---|---|---|
| カウンタなし(`impact_counter_no_trigger.json`) | 1.81→2.99 | 144.33→277.86 | 0 |
| トリガーで 1 行更新(`impact_counter_trigger_one_row.json`) | 3.13→1.79 | 792.43→8.13 | **538** |

行ロック待ち 538 回は競合の証拠ですが、**遅延の差はノイズの範囲で、この負荷では遅くなることを示せていません。**

カウンタを 16 行に分けて読むときに `SUM` すると、競合は明確に減りました(各 1 回、`54-EXP-SOL-9.json`)【実測】。

| 書き込み手 | 1 行: コミット数, p50 / p99 ms | 16 行: コミット数, p50 / p99 ms |
|---|---|---|
| 4 | 15,107, 2.0 / 4.1 | 30,076, 0.99 / 2.31 |
| 16 | 13,724, 6.75 / 48.13 | 53,856, 2.29 / 4.3 |
| 4、長いトランザクションが 1 行を保持 | **4**, 8012.28 / 8013.5 | 48, 2.77 / 7984.61 |

**長いトランザクションが持つカウンタ行は、1 行なら書き込み全体を止めます。** 分けても、その行に当たった書き込みは待ちます。

**ずれる経路**:

- **`TRUNCATE` はトリガーを起動しません。** 5 万行の表で、実数 0、カウンタ 50,000 になりました(`49-EXP-SOL-5.json`)【実測】。パーティションの `DROP`/`TRUNCATE` も同じと考えられます【推論】。
- `REPLACE` と `INSERT ... ON DUPLICATE KEY UPDATE` は、INSERT と DELETE の両方のトリガーを揃えれば、ずれませんでした(同)【実測】。
- FK の CASCADE / SET NULL による子の変更は、8.4 ではトリガーを起動しません(変数がなく 1193)。9.7 と 26.10 の既定でも起動しません。**変更を行うセッション**で `enable_cascade_triggers=ON` にすると、子 10 行の DELETE / UPDATE トリガーが起動しました(全 5 版、`58-EXP-O2-3-*.json`)【実測】。カウント接続ではなく、書き込むアプリのセッションの設定を確かめ、補正を二重にしないでください。`innodb_native_foreign_keys` は実行中に変更できず(1238)、ON の動作は【未計測】です。
- トリガー導入前の変更、`sql_log_bin=0` の変更、レプリカだけへの変更【推論】。
- アプリのカウンタは、書き込みと同じトランザクションで更新しないとクラッシュでずれます【推論】。

**初期値**: 既存の表では、件数と差分を同じ時点で接続しないと、ずれが永続します。書き込み中に数えた値で初期化すると -32 ずれました(変更 3,119 件)(`49-EXP-SOL-5.json`)【実測】。次のどちらかにします。

1. 計画的に書き込みを止めて、`COUNT(*)` を初期値にしてからトリガーを有効にします。ずれは 0 でした(同)【実測】。
2. レプリカを使う方法(ROW 形式で、カウンタ表も複製される場合)。トリガーを入れてカウンタを 0 から始めます。レプリカの適用を止め、同じ状態で `COUNT(*)`=N とカウンタ=D を読みます。primary で `c = c + (N - D)` とします。**ずれは 0 でした**(`N`=49,958、`D`=-42、同)【実測】。ただしこの実験は、止めたレプリカを 1 つの REPEATABLE READ のスナップショットで代用しています。
   - この補正は**一度だけ**適用します。補正 ID を一意キーの表に入れる処理と同じトランザクションで更新します。再試行は「適用済み」で拒否され、ずれは 0 でした。**補正 ID なしで再試行すると 50,000 ずれました**(同)【実測】。
   - **定期照合**も同じ手順で、N と D が同じ時点の値であることが条件です。

## 10. 検討した別案

レビューの候補を含めた判定です。

| 候補 | 判定 | 理由 |
|---|---|---|
| 1 文の `COUNT(*)`(時間上限付き) | **採用**(数える索引に書き込みが触れないときに最速) | §3。MDL と undo の代償があるので、DDL を排除できるときに上限を延ばす |
| 分割 | **条件付きで採用** | 短いトランザクションで1文ごとのMDL・undo保持を短くする。総負荷は残り、合計は一瞬の値ではない |
| `EXPLAIN` の `rows`、`expiry=0` の `TABLE_ROWS` | **採用**(概数) | §4 |
| `mysql.innodb_table_stats`, `SHOW TABLE STATUS` | 補助 | 同じ統計に由来。`n_rows` は再計算まで古い |
| `INNODB_TABLESTATS.NUM_ROWS` | 条件付き補助 | PROCESSが必要。STATS_INITIALIZEDを併読し、未初期化0を空表と扱わない。未コミットDMLも影響する。主文書§2 |
| `PARTITIONS.TABLE_ROWS` | **採用**(パーティション表の概数) | 666,324 / 666,700(`24-EXP-R10.json`)。1 回のみ |
| 閉じた範囲の確定値 + 新しい範囲の増分 | **条件付きで採用** | 下記 |
| `FORCE INDEX (PRIMARY)` の 1 文 | **短い上限で試す候補** | 旧reqmix2の順位は失敗分類・反復・終了確認を再監査中で採用根拠にしない。0gの限定観測は§13。毎秒 100 文では差が確立せず、数える索引に触れない書き込みでは遅く、書き込み p50 を上げる(§3)。大きさと速度による分かれ目は結果待ち(§11) |
| 主キーだけの表で `innodb_parallel_read_threads` を下げる | **不採用** | 約 1.9 倍の表でも既定の 4 が速い(§3) |
| `innodb_parallel_read_threads` を上げる | **不採用** | 二次索引では差がない。`t_dense` の `PRIMARY` では 8 で書き込み p50 が 12.5 ms に上がる(§3) |
| 複数接続の並列カウント | 条件付き候補 | 主キー範囲で 1 接続 31.26 秒、4 接続 17.04 秒、書き込み p50 は 1.22 / 2.15 ms(各 1 回、`54-EXP-SOL-9.json`)。合計は同時点ではなく、MDL と停止の対象も増える |
| 専用の小さい索引 | 繰り返し数えるなら候補 | 50 万行で `PRIMARY` 45,568 ページ、小さい索引 673 ページ。追加 0.4 秒、歩行は 0.098→0.064 秒(`54-EXP-SOL-9.json`)。書き込み負担はこの 1 回では見えない |
| 不可視索引で数える | 不採用 | `optimizer_switch` か `SET_VAR` が必要で、なければ 1176。SQL 3 も除外する(同) |
| 余力のある専用replica | **条件付きで採用** | 通常は適用を止めずCOUNTする。取得先の時点と共有資源の負荷を確認する(§7) |
| replicaの適用停止 | 所有者が時点固定を必要とする場合だけ | 意図的な遅延、停止要求の遅効、復旧確認と継続監視を所有者が扱う別運用(§7) |
| クローン | 未計測 | §7 |
| 集計カウンタ | 頻繁に読むなら候補 | §9。複数行に分けると競合が減る |
| binlog / CDC の差分 | 未計測 | 位置の管理と再実行の排除が必要 |
| `performance_schema` の INSERT / DELETE 操作回数の差分 | **不採用** | コミットと削除では一致するが、ロールバックと `REPLACE` は実際の変化 0 に対し +100、`TRUNCATE` は -10,000 に対し 0(`54-EXP-SOL-9.json`) |
| `MAX(id)-MIN(id)+1` | 不採用 | 欠番で桁違いにずれる(§4) |
| ヒストグラム、`n_diff_pfx` | 不採用 | 総行数を確定できず、`EXPLAIN` の `rows` に勝つ根拠がない【推論】 |
| キー範囲からの固定標本 | **不採用** | 欠番の多い `t_sparse` で種により -100% と +3.19%。ほかは 0〜0.46% だが読み取りは 0.08〜0.5 秒で、`EXPLAIN` より遅い(`54-EXP-SOL-9.json`) |
| `COUNT(1)`, `COUNT(id)` | 別の方法ではない | `t_dense` で `COUNT(*)` 8.36〜11.16 秒、`COUNT(1)` 8.09〜10.48 秒、`COUNT(id)` 7.61〜9.02 秒で差は確立しない(各 3 回、`requested_wide_count_forms.json`) |
| `COUNT(非索引列)` | **不採用** | 行全体を読む。60 列 300 万行で 4.47〜11.99 秒、`COUNT(*)` は小さい索引で 0.113〜0.129 秒。NULL 可の列は 3,000,000 行に対し 2,000,010 と別の値(`requested_wide_count_forms.json`) |
| READ UNCOMMITTED で数える | 不採用 | 未コミット行を数える(§1)。高速化も見られない(§7) |

**増分の条件**: 閉じたパーティションの確定値を再利用すると、300 万行で全域 27.3 ms、増分 8.9 ms で一致しました(`52-EXP-R16.json`)【実測】。ただし前提が崩れると黙ってずれます。**`TABLE_ID` と `UPDATE_TIME` の両方を見ないと検知できません。**

| 閉じた範囲で起きたこと | 増分の誤差 | `TABLE_ID` で検知 | `UPDATE_TIME` で検知 |
|---|---|---|---|
| 更新 | 0 | いいえ | はい |
| 削除 | 125 | **いいえ** | はい |
| 遅延到着 | -1,000 | **いいえ** | はい |
| `EXCHANGE` | 745,000 | はい | **いいえ** |
| `TRUNCATE` | 751,000 | はい | はい |

パーティションのない追記表では、古い行の削除を検知できず 1 ずれました(同)。

**両方が一致しても、閉じた範囲が変わらなかった証明にはなりません。** `UPDATE_TIME` は秒単位なので、確定値を取ったのと同じ秒の変更は見えません。同じ秒の遅延到着は 5 回中 5 回、削除は 5 回中 3 回、どちらの信号も変えずに 1 行ずれました。秒をまたげば検知しました(`52a-EXP-S6-INCREMENTAL-SAME-SECOND.json`)【実測】。`UPDATE_TIME` は再起動に加え、InnoDB のデータ辞書キャッシュから追い出されても失われます【文書】。**不変性を運用で保証できない範囲は再カウントし、全体の定期照合と併用します。**

## 11. 未完了・未計測の主な項目

判断への影響の順です。括弧内はレビューで合意した実験の ID です。

**残っている不確かさ**(`bench/requested/README.md` が対応表です):

1. **どの索引の 1 文が速いか(EXP-O10-PRIMARY-SCALE、`0g`〜`0k`)**: プールの 4〜8 倍の表で、飽和していない書き込み速度での比較です。0g/0iは保存観測がありますが0h/0jは部分結果です。予定反復欠落を解消するため方式群・反復別のスクリプトへ分割しました。修正後の白紙実行待ちで、§1 と §7 の短い上限も無影響の保証ではありません。
2. **毎秒 100 文の索引列の更新で起きた 66.806 秒の分割と秒単位の書き込み遅延(EXP-O10-INDEXED-100-STALL、`0d`)**: 0dは正常終了した保存観測があります。旧事象の原因を単独の索引要因とは断定せず、回復・全区間の書き込みを含めて固定runnerの再計測後に評価します。今回も基本負荷試験中の中断で要求実験に到達せず、この要求の再計測は未着手です。
3. **毎秒 800 文の散らばる書き込みでの影響と分割の完走(EXP-O10-ROW-CEILING、`0e`, `0f`)**: ラボの限界に近く対照がありません(§3)。行数の上限での再試験は結果待ちです。
4. **`PRIMARY` のない表(EXP-O10-NOPK-FORCE、`0l`)は未実行です。名前がなければPRIMARYを強制せず、適用条件を確認した分割か余力あるreplicaへ進みます。** STOPの期限超過と復旧の`0c`は正常終了し、§7へ反映しました。
5. **`PRIMARY` の並列読み取りが遅くなる表の大きさ**: 1.9 倍では並列が速く、4 倍の `t_dense` では遅いので、分かれ目は不明です(§3)。
6. **暗号化と幅広い表**: 91の3版の再計測は正常終了しましたが、キャッシュ状態の同等性は示していません。操作と読取量を伴う観測として扱い、暗号処理だけの倍率には使いません。96・97には旧負荷生成器の観測があり、01a/01bには保存則付きの50/100列の保存観測があります。修正コードを白紙実行して適用範囲を再確認します。適用範囲と暗号化方式は主文書§3を参照してください。3版の正常終了はキャッシュ同等性を意味しません。旧観測も新観測も暗号処理倍率の根拠にはしません。
7. **92/93/94**: 92は64観測が揃いましたが終了コード不明で、実行成功とは区別します。93は初期化状態を併読した再試験まで、94は権限・DDL待ち・最終件数まで正常終了しました。主文書§2/§3と保存した観測を参照してください。

**このラボでは測らないもの**: MEMORY の片側再起動と MyISAM のクラッシュ後(要求は取り下げ済み。各サーバーの状態を数える規則は変わらない)、Group Replication とプロキシ、マネージドサービス、ネットワークストレージ、大量の表を巡回するコスト、本番規模の幅広い表（合成50/100列は計測済み）、数時間の undo 滞留、relay log の容量、STATEMENT 形式。一時表、一般表領域、オンライン再構築中の表も保証の範囲に含めません。暗号化の追加検証と制限は主文書§3と§7にあります。
