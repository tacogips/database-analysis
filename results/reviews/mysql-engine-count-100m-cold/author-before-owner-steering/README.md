# Dedicated 100M-row COUNT comparison with a fresh DB buffer per sample

Owner entry point from repository root: `mise -C mysql/engine-count-100m-cold run all`. The task runs `mise exec -- ruby lab.rb all` with installed Ruby 4.0.9. No build, dependency download or image pull is performed. Author/reviewer work is offline; the root owner runs this only after the author process is terminal and the old runtime's cleanup is independently verified. This runner does not inspect, reuse or delete the old experiment's runtime/data.

## Fixed experiment

Exactly two fresh loads, InnoDB then MyISAM, one engine at a time. Each has 100,000,000 rows, 100 stored columns: `id BIGINT UNSIGNED NOT NULL PRIMARY KEY`, `c001..c099 INT NOT NULL`, nominal scalar payload 404 bytes. The same deterministic generator makes c001 a 100k-value permutation, c002 about 80% zero by id blocks, c003 high cardinality, c004..c099 constants. The 100k-row sequence produces 1000 committed INSERT SELECT batches with immediate ROW_COUNT receipts and a response boundary after COMMIT. No table data is reused or committed. MyISAM is nontransactional; a COMMIT receipt does not imply atomicity or rollback.

Four conditions, three plain `SELECT COUNT(*) FROM lab.count_target` each: InnoDB PK only; same rows plus narrow `k_count(c001)`; replace it with `k_count_v2(c001,c002,c003)`; fresh MyISAM PK only. The actual narrow catalogue drives the recorded decision to add a wider reference. Optimizer choice is observed, never forced. There are exactly twelve full-table COUNT requests, no COUNT(1), business WHERE, extra validation COUNT, explicit locking read, service workload or intentional contention. Index DDL is fixture setup only; load, each index build, each restart and each COUNT are timed separately.

## Cold-buffer definition and lifecycle

Before EVERY sample, including the first after load, first after each index build, and repeats: close/reap all loader/fixture/reference/previous count CLIs; orderly stop the owned mysqld; require container exit0 and attach exit0/reap; restart the SAME container ID, nonce and datadir with unchanged Compose config; wait at most120s for final mysqld PID1/socket readiness and validate actual image, resources, boot globals and UUID. No second COUNT runs in one boot. InnoDB has one initial load boot plus nine count boots; MyISAM one initial load boot plus three count boots. All fourteen attach processes, actual PIDs/start times, uptime, readiness failures, command/client PIDs, logs, actual exits and reap records remain in evidence. A failed stop/start/readiness/reap aborts the stage and preserves the failed sample; cleanup may force an owned runtime to terminate but this cannot be an accepted cold reset.

Startup explicitly sets `--innodb-buffer-pool-load-at-startup=OFF`, `--innodb-buffer-pool-dump-at-shutdown=OFF`, `--innodb-flush-method=O_DIRECT`. Every boot verifies these globals and default `innodb_fast_shutdown=1`; no crash/recovery reset, SQL_NO_CACHE, FLUSH TABLES, global drop_caches, macOS purge, VM restart or new mount is used. MyISAM's process-local key cache also starts fresh; its stored engine row-count optimization remains enabled and is not a query-result cache.

Cold buffer means a fresh verified mysqld with preload disabled and no previous table full scan that boot. It does **not** mean every target root/metadata page is absent. A fresh dedicated count CLI sets/verifies autocommit1, READ COMMITTED, lock_wait_timeout3s and max_execution_time1200000ms. Ownership identity is `(boot ordinal, server UUID, connection ID)`; connection IDs may repeat across boots. Before manual checks and again just before the timed request, InnoDB target pages are grouped by INDEX_NAME/PAGE_TYPE with `COUNT(*)` on information_schema.INNODB_BUFFER_PAGE filtered to exact TABLE_NAME `` `lab`.`count_target` ``. This is a buffer-metadata count, not another scan of table rows. SQL/raw/ns, counts and residual pages are saved. Metadata/background activity may touch a few pages. Unexpected fully resident target/index evidence makes cold policy unproven and aborts before COUNT. MyISAM has no applicable InnoDB target-page proof; boot identity and pre-COUNT Key_* global counters are its reference.

O_DIRECT is verified as a guest setting, not proof of physical SSD reads or empty OS caches. Guest OS, VM, virtiofs, macOS host and device caches may retain data; their state is unknown. Fixed order, host cache reuse and index-build warming remain confounders. No claim of fully uncached storage, causal engine/index speed, other hardware performance or production SLO follows.
